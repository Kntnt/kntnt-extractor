# A failed poll relays a throwable's own message, which may carry a filesystem path or a query fragment

A failed extraction's poll now carries a reason built around the throwable that killed the build ([0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md), issue #25). Most of that string is the plugin's own composition — the throwable's class, the origin file named relative to the installation root, the line, and the chunk that was being packaged — and every part of it is either the caller's own selection or text this project wrote. One part is not: the throwable's own message, relayed verbatim up to `Dispatcher::THROWN_MESSAGE_BOUND` characters. **That string is arbitrary by construction and may carry a filesystem path, a fragment of SQL, or anything at all that third-party code hooked into the packaging chose to throw.** This decision keeps it, says so plainly, and is the first place in this repository where the rule about what a failure may disclose is actually written down.

Truncating it bounds the **size** of a disclosure and not its **kind**. A 300-character head accommodates an absolute path comfortably and accommodates a SQL fragment by construction — a `PDOException` states what went wrong first and elaborates afterwards, which is exactly why the head is the half worth keeping. No bound at any length makes the string safe; it makes it small.

## The rule this replaces, and how it came to need deciding

The original rule was stated in `error_of()`'s docblock and in `Extraction_Job`'s `$error` line, and it was absolute: a throw's message *"is never captured, because it could carry a filesystem path or a fragment of SQL"*. The commit that began recording throwables replaced the first of those sentences with a claim that the reason is *"bounded and trace-free so the arbitrary string it relays cannot carry a whole query or a call stack out to the caller"* — where "whole" carries the entire argument, and a fragment, which is what the original sentence was about, is precisely what survives. The second sentence was not touched, so the repository stood with two incompatible statements of one rule, the surviving one being the one that matched the original decision.

**The invariant had been moved to fit what the implementation achieved, rather than the implementation written to meet the invariant** — and nobody decided that. The edit was small enough to read as a routine docblock refresh, which is why it passed two sessions. That is the defensible finding, and it is narrower and harder to dispute than any claim about the disclosure itself: whether the widened rule is acceptable is a judgement that belongs in front of a maintainer, not one to settle inside a comment. This ADR is that judgement, taken deliberately. The weasel framing is deleted; both docblocks now say what the string may carry and point here.

**This is not a vulnerability claim and should not be argued as one.** The reader is the polling **owner** — authenticated, holding `kntnt_extractor_operate` *and* `manage_options` ([0002](./0002-authn-app-password-authz-operate-plus-manage-options.md)) — and a WordPress administrator holding `manage_options` on an ordinary install can already reach the site's filesystem layout by routes this plugin neither provides nor can close. What was missing here was never protection. It was a decision.

## Why the message is kept

This ticket exists because a six-hour production run died at 97.8 % and left one uninformative sentence (`docs/measurements/2026-08-18-production-run.md` §3). Dropping the relayed message partially recreates that. A `PDOException` reading *"Table 'x' doesn't exist"* is the entire diagnosis, and its class alone says almost nothing; the same is true of a permission fault, a corrupt row, or a driver error. The chunk name and the message answer different questions — **the chunk names *which* resource, the message names *what went wrong* with it** — and the one observed failure where the chunk alone would have sufficed is a case where the fault happened to be the resource's disappearance. Generalising from it to "the message is dispensable" is exactly the reach that measurement's own "What this does not establish" section warns against.

Three alternatives were considered and each is recorded as rejected rather than unconsidered.

**Sanitise the message** — strip path-shaped and query-shaped content before storing. Most faithful to the original rule, and the most fragile thing here to write: the string is arbitrary by definition, so the filter is a guess about shapes, permanently behind whatever PHP, PDO, and third-party code actually emit. A filter that silently mangles the one sentence that was the whole diagnosis is worse than either honest option.

**Drop the message, keeping class, origin and chunk.** This stays a defensible trade and is the alternative worth re-reading if this decision is ever reopened — but it must then be argued on the ground that the diagnostic loss is *acceptable*, never that the loss is *small*, because one run does not establish that.

**An allow-list with a per-record discriminator** — this repository's own established answer to "what may a value disclose" ([0018](./0018-a-defines-value-discloses-only-from-an-allow-list-with-a-per-record-discriminator.md)), adopted there precisely because "what can this field safely carry" was judged not answerable by a size bound, which is the same judgement being made here. It loses on a disqualifier worth stating so it is not re-derived. The cheap discriminator is **provenance**: relay a throwable the plugin authored itself in full, withhold a foreign one. That split excludes precisely the case that is the strongest argument for keeping the message at all, because a `PDOException` is foreign by construction. Keeping that case would need an allow-list over message *shape* — per driver, per error code, re-derived whenever a PHP or PDO release changes what it emits — which is more machinery than this problem carries and would be the first thing in this repository to rot. **The cheap version does not do what the expensive version is for.**

## What still carries no absolute path

The plugin's own composition is a separate matter from what it relays, and this decision changes nothing about it. The origin is named relative to the installation root, the same rule `GET /environment` applies to every path it reports, and for the same reason: one sentence disclosing one file root-relative — the packaged chunk, via `Dispatcher::stalled_chunk()` — and another absolutely would be two rules with a reason for neither. **What this decision widens is only what the plugin passes through, never what it writes itself**, and the distinction is the difference between a systematic disclosure of a site's layout, which [0018](./0018-a-defines-value-discloses-only-from-an-allow-list-with-a-per-record-discriminator.md) governs and a client ports into a local file, and one incident string on one failed job that a human reads while diagnosing it.

`THROWN_MESSAGE_BOUND` stays at 300 and stays a non-knob. Raising it would widen what a failed poll discloses, which is a decision about this rule rather than a tuning choice; lowering it only breaks the diagnosis it exists to provide. Its own docblock is the one place in the repository that never misstated this — *"a PDO or filesystem error carries a query fragment or a path, and third-party code hooked into the packaging carries anything at all"* — and it is left exactly as it stands.

## Three sinks, three lifetimes — and one that is not a sink

The rule governs a string in three places, not one REST member, and they have different lifetimes.

**The poll response.** `GET /extractions/{id}`'s `error.message`, read by the owner and discarded. This is the sink the rule is usually imagined to be about, and it is the shortest-lived of the three.

**The persisted job record.** `Extraction_Job::to_array()` writes the reason into `state.json`, which lives on disk until the TTL sweep reclaims the job. So the rule governs a file, not only a response body — and there is a bound on how long that file can live. Because a throw leaves `error` null and records its reason in a field of its own, the record is not a pre-adaptation stall, so `Sweeper::reclaimable()` treats it like any other failed record and the ordinary TTL applies ([0019](./0019-every-purging-actor-takes-the-tick-lock-an-ownerless-artifact-is-reclaimed-server-side.md), [0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md)). The records the sweep spares indefinitely are legacy *stall* records, whose reason the plugin composed itself from the caller's own selection and settings it already discloses, and which are safe by construction. **That bound is a consequence of fixing the routing, not of this decision.** Every routing option considered on #25 produces it, by three different mechanisms; only the unfixed status quo — the relayed message sitting in `error` — lacked it, and that is the one combination in which an arbitrary relayed string could sit forever in a record nothing reclaims. It is the reason this decision is safe to take at all, and the reason it must not ship without the routing fix.

**The consuming client's output.** `kntnt-wp-skills` carries the response's `error` through: its poll discipline defines failure as `state == "failed"` *"(capture the reported `error` verbatim)"*, its poll helper writes per-poll lines to a run log, and the failing role puts the captured value in its own evidence block. So an arbitrary relayed string reaches that repository's operator-visible run output, and from there whatever its transcript or run log retains. **An ADR here that says the poll may carry arbitrary relayed strings is implicitly a statement about what that repository may write down**, and it is named as such rather than left for its next reader to discover. Whether the client should treat such a string differently — bound it, mark it as relayed rather than authored, or surface it unchanged — is that repository's decision and is not taken from here.

**The audit log is not a sink, and one sentence is cheaper than re-establishing it.** Its entry carries `ts`, `user_id`, `user_login`, `api_version`, `job_id`, the two table lists and a hashed files summary, and has no error member at all; `Audit_Log::record()` is hooked on `kntnt_extractor_job_ready`, which the driver fires only on the ready transition, so a failed job never reaches it. Nothing in [0006](./0006-file-based-audit-log-random-name-age-rotated.md)'s age-rotated file is governed by this rule.

## Where the rule was cited before, and where it lives now

The non-disclosure rule has been cited to [0007](./0007-pure-php-chunked-resumable-loopback-driven-extraction.md), which contains no disclosure or opacity rule of any kind — its subject is pure-PHP chunked resumable extraction driven by a loopback loop: no external binaries, resumability, the watchdog. Of 27 citations of that ADR across `classes/`, exactly two leaned on it this way: `Dispatcher::stall_reason()`'s *"the opacity rule (ADR-0007)"* and `error_of()`'s docblock. Both now point here. **The other 25 are legitimate and are untouched.** That the rule the docblock refresh rewrote had no ADR standing behind it in the first place is plausibly why rewriting it felt like editing prose.

## Why this does not move `API_VERSION`

Under [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md) the integer bounds the *artifact's* shape — the container's framing, segments per resource, the sealed index, reassembly order — and none of that moves. Under [0018](./0018-a-defines-value-discloses-only-from-an-allow-list-with-a-per-record-discriminator.md)'s narrower second ground it also moves when an already-shipped client's existing behaviour would become unsafe against the new server, undetectably and without its consent; that does not apply either. `error.message` was always one string of prose whose content the client is documented to surface rather than parse, and it still is. There is no new member and nothing for an old client to act on differently. `API_VERSION` stays `7`, and no `honours` entry is added: `honours` names caller-visible *behaviours* a client can choose to use, and this is a statement about what an existing member's existing content may contain.

## Consequences

- **The poll's `error.message` may disclose a filesystem path or a query fragment to the owner, on a failed job that threw.** That is the decision, stated in the one place a reader will look for it, rather than implied by a bound.
- The two docblocks that stated the old rule now agree with each other and with this ADR. The repository no longer carries two incompatible statements of the same rule, which is the condition that let the rule be rewritten unnoticed.
- **This decision is conditional on the routing fix, which shipped with it.** Keeping the relayed message while the thrown reason still lived in `error` is the one combination that puts an arbitrary relayed string into a record the sweep spares indefinitely. Neither half is alarming alone; the pair is the worst cell in the grid. Anything that would put a relayed string back into `error` reopens this decision, not just that one.
- A reader diagnosing a failure gets the sentence that is often the whole diagnosis, at the cost stated above. The alternative was measured against the run that produced this ticket, not against a hypothetical.
- **Nothing here bounds what a hostile hook can put in the string.** Third-party code hooked into the packaging can throw whatever it likes, and 300 characters of it reach the owner. The exposure is bounded by who may read a job — the owner, and only the owner — not by anything about the string.
- `kntnt-wp-skills` inherits an arbitrary string into its run output and logs. Its handling is its own decision; this ADR names the exposure so that decision is taken knowingly rather than by default.
- The non-disclosure rule has an ADR of its own for the first time. The next change to what a failure discloses has somewhere to be argued, and `ADR-0007` stops being cited for a rule it never contained.
