# The create payload carries the file-part budget, in the range the Config seam already permits

The one setting that decides whether a multi-hour extraction survives could not be chosen by the caller. `chunk_size` bounds a file part, and `docs/measurements/2026-08-19-chunk-size-curve.md` measured what it is worth on a real production host, holding the file, the host, the build and the method fixed: 256 KB packages a 36 MB file in 85 s, 1 MiB in 108 s, 2 MiB in 184 s, and 4 MiB manages two parts in twelve minutes and does not finish. The shipped `DEFAULT_CHUNK_SIZE` of 8 MiB sits far past a threshold that makes runs impossible rather than merely slow, and the run that finally completed against that site (`docs/measurements/2026-08-19-successful-run.md`) differed from the six-hour failure before it in exactly one deliberate way: the knob was lowered to 256 KB. **That value is host-specific and there is no reason to believe it transfers.** Until now the only levers were the `KNTNT_EXTRACTOR_CHUNK_SIZE` constant and the `kntnt_extractor_config_chunk_size` filter, so a client that wanted to probe for the value the curve was measured with — or simply to use the one it had already measured — had to get code edited onto production first.

`POST /extractions` now accepts an optional `chunk_size` member carrying that budget in bytes, persisted on the job like any other per-job budget. Omitting it is byte-for-byte the previous behaviour: the member resolves to zero, which is the record's own long-standing "package at the Config default", and every job that has ever been created has carried exactly that.

## The accepted range is derived, not chosen

Rule R4 — constants are measured, not chosen — is what makes the range the interesting part of this decision rather than a formality. The temptation is a `MIN_CHUNK_SIZE`/`MAX_CHUNK_SIZE` pair, and picking either would be exactly the mistake [0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md) already recorded about `DEFAULT_CHUNK_SIZE`: a number chosen without measuring the host, then trusted.

So the range is read off the seam this member feeds, and nowhere else. `Artifact_Builder::configured()` resolves the `chunk_size` knob as `max( 1, is_numeric( $configured ) ? (int) $configured : $fallback )` — a floor of one, deliberately and for a stated reason ("at one byte a slice still renders its first row, so the build advances a row at a time rather than stopping"), and no ceiling of any kind. The per-job channel this member actually writes to agrees independently: `Artifact_Builder::budgets()` honours a job's own size only while `$job->chunk_size > 0`, and `Extraction_Job::from_array()` accepts a persisted budget only as an integer at or above zero. **An integer of at least one, unbounded above, is therefore exactly the set of values the existing seam can put in force**, and it is what the payload member accepts — nothing wider, nothing narrower, and no new constant at either end.

The absence of a ceiling is a derived result and not an oversight. What a given host survives is a measured, host-specific fact this endpoint is in no position to know; the curve above is one host's, and a cap set from it would be a guess dressed as a bound everywhere else. A request for a budget the host cannot survive is not unhandled either — it is the case the stall adaptation exists for, and it is caught by measurement rather than by prediction. See "What this does not fix".

The *type* discipline is separate from the range and is the create path's existing one: a member arrives as its JSON type or it is malformed, the way a non-boolean `strict` already is. A fractional number or a string-wrapped one is refused rather than coerced, even though the seam's own `is_numeric()` would have coerced it, because the contract a caller writes against is the payload's, not the filter's.

## Where it sits in the ladder, and what it does not disturb

The check runs immediately after `strict`'s and before the public-key check — the two optional scalar members are validated together, refused the same way, and the ordering [0003](./0003-generic-manifest-and-table-list-no-server-side-categorisation.md) fixed is otherwise untouched: the two size caps of [0020](./0020-two-additive-caps-bound-one-unauthenticated-request-not-the-rate-of-them.md) still stand ahead of everything, and the 404-before-403 disclosure ordering is unchanged. An out-of-range value is `422 kntnt_extractor_malformed_body`, the code the create path already uses for every malformed member, and not a code of its own: a client that already handles a malformed body handles this without learning anything new.

A requested budget and an adapted one are the same field on the record on purpose. A stall halves what the chunk actually spends ([0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md)), and it now halves from the caller's number rather than from the Config default — which is what a caller asking for a size means: a starting point the run may walk down from, never a floor under it. Nothing about the stall counter, the floor, the resume condition or the sweep's sparing rule changes; `Extraction_Job::is_pre_adaptation_stall()` keys on the *absence* of the schema-8 budget keys, and a create has always written them.

## Why this does not move `API_VERSION`

Under [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md), `API_VERSION` bounds the *artifact's* shape — the container's framing, segments per resource, the sealed index, and reassembly order — and this changes none of it. A file is still packaged as bounded parts, still recorded in the index once per part under its installation-root-relative path, and still reassembled by concatenating every segment carrying that name in index order. How many parts a given file yields was never a contract term and could already differ between two sites, or between two runs on one site once a stall adapted the budget mid-run.

Under [0018](./0018-a-defines-value-discloses-only-from-an-allow-list-with-a-per-record-discriminator.md)'s narrower second ground, the integer also moves when an already-shipped client's *existing* behaviour would become unsafe against the new server, undetectably and without its consent. That does not apply either, and the reason is the strongest available one: an old client does not send this member at all, and a request without it produces the same job, the same record and the same artifact it produced before. There is nothing for such a client to act on differently, unsafely or otherwise. This is precisely the additive shape `honours` exists for, so `chunk_size` is named in `Status_Controller::HONOURED_BEHAVIOURS` and `API_VERSION` stays `7`. No coordinated release with `kntnt-wp-skills` is required.

Absence from that list is the only signal a client has, which is why the name is added in the same change as the behaviour rather than afterwards — [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md) records that a behaviour shipping without being named there is the `strict` failure repeated, and now a maintenance error rather than an inherent limit.

## What this does not fix

**It does not choose a default.** What the shipped `DEFAULT_CHUNK_SIZE` should be is a separate decision on separate evidence, and this change deliberately leaves it at 8 MiB. A site that never sends the member is exactly as exposed to that default as it was, including to the finding that it sits past the one measured threshold. This gives a caller a lever; it does not move the one the site starts from.

**`honours` cannot tell a caller which value to send.** The list is presence-only by design, so `chunk_size` says only that the member is accepted. The value that survives is host-specific and the only way to establish it is the way the curve was established — by measuring on that host. A client that wants one can now probe for it over the API instead of by editing production, which is the actual improvement here.

**A caller can ask for a budget the host cannot survive, and the range does not stop that.** There is no ceiling, so a request for 64 MiB on a host that dies at 4 MiB is accepted. That is a deliberate consequence of refusing to invent a bound: the run then stalls, the adaptation halves the budget it is actually spending and carries on, and the job calibrates itself to the host — the mechanism [0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md) built for precisely this. An oversized request costs attempt windows rather than the run. The honest statement is that a bad value is survivable, not that it is free.

**Nothing bounds this member against the request-cost caps.** `chunk_size` is one small integer; it adds no work to the pre-authorization path [0020](./0020-two-additive-caps-bound-one-unauthenticated-request-not-the-rate-of-them.md) bounds, and it is checked with two comparisons after that ladder's caps have already run. It neither widens nor narrows what an unauthenticated caller can provoke.

## Consequences

- `POST /extractions` accepts an optional `chunk_size` — an integer of at least one, in bytes — carrying the job's own file-part budget. Omitted, the job packages at the Config default exactly as before; the member is not echoed on the create or poll response, since the job's own budget was never part of either.
- The accepted range is the Config seam's, derived from `Artifact_Builder::configured()`'s `max( 1, … )` and from the absence of any ceiling there. No constant is introduced for either end, and a future maintainer who wants one should measure a host first (R4).
- A value outside the range — zero, negative, fractional, string-wrapped, or any non-integer — is `422 kntnt_extractor_malformed_body`, the create path's existing malformed-member refusal. No new error code, no new status.
- The check runs immediately after `strict`'s and before the public-key check. Every other step of the validation ladder, and the 404-before-403 ordering, is unchanged.
- The stall adaptation halves from the requested budget rather than the Config default. A requested size is a starting point, never a floor, and the floor of one and the terminal-at-the-floor rule are untouched.
- `chunk_size` joins `Status_Controller::HONOURED_BEHAVIOURS`; `API_VERSION` stays `7` and no coordinated release is required.
- The shipped default is unchanged and remains a separate decision on separate evidence.
