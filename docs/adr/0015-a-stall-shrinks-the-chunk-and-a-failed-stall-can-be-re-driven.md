# A stall shrinks the chunk, and a failed stall can be re-driven from persisted progress

A chunk that dies outside PHP — the host killing the worker at a memory or execution-time limit, so no `catch` runs — is no longer a death sentence for the job. The attempt counter [0013](./0013-tables-are-dumped-in-keyset-paginated-slices-across-ticks.md) already detects exactly this shape: the same offset begun repeatedly, finished never. On that signal the driver halves the bounds the chunk that died actually spends, persists them on the job, clears the attempt counter, and continues. The job stays `running`. Only a chunk whose bounds are all at their floor still fails the job, because retrying that would reproduce the kill forever.

A job stalled and failed by a release that could do none of that — an on-disk record from 0.5.1 or earlier, which failed at the first wall — is re-driven from the progress it already persisted. The next tick, or the watchdog, re-enters it into `running` with a fresh attempt window and adapted budgets. `Sealed_Writer::resume()` already truncates the in-progress container (and its index sidecar) back to the committed byte lengths, so a chunk that was appended but never acknowledged cannot be duplicated. What was missing was permission, not information.

The two halves belong together. Resume without adaptation walks straight back into the wall that spent the attempt counter; adaptation without resume leaves every record an earlier release stranded unrecoverable, and discards everything it packaged. Together an upgrade over a dead run becomes "carry on" instead of "start over".

## Ask before shrinking

Shrinking is not the first remedy, only the durable one. Before a tick packages anything it asks the host for execution time and memory. That costs one call each and needs no search, and where a host limit rather than the work itself was the killer it removes the search entirely. The pre-raise and post-raise readings are persisted on the job at the first tick, because a stall reason written hours later would otherwise report that later process's limits rather than the ones in force when the chunk died.

Every part of that ask can fail. A managed host may lock either directive or disable `set_time_limit()`; a container cap kills the worker whatever `memory_limit` says; and PHP's timer does not count time spent in system calls on Unix, so even a granted raise does not prove the clock was the killer. None of that argues against asking. A refused ask leaves the run exactly where it was, and the outcome is information either way — which is why the stall reason reports what was asked for beside what the host granted, reading both pairs from the record. Equal pairs mean the host refused and only its own configuration can help. Differing pairs mean the raise was granted and the chunk died anyway, so the kill came from above PHP or from the kernel — a diagnosis the attempt counter alone can never reach, and one that tells the operator to stop shrinking.

## Why two attempts, not three

`max_stall_attempts` was three when exceeding it failed the job. A false positive then cost the whole run, so several attempts were worth their price. Exceeding it now halves the chunk and carries on, so a false positive costs throughput for the remainder of the run and nothing more — while every attempt costs a full execution-time limit, paid 23 times over on the way from 8 MiB to the floor, and paid only on a host that is already failing. The balance moved, so the number moved with it.

It does not move all the way to one. The kill is usually deterministic and a second attempt at the same size usually dies the same way, which is the argument for one. But not every kill is about the size: an FPM reload, the kernel's OOM killer choosing this worker because of a neighbour, and a momentary I/O stall on a networked mount all present identically to the counter. At one attempt each of those permanently halves the budget, which never recovers within a run. One confirmation before an irreversible decision is proportionate; a third is not. If the budget ever learns to recover on sustained success, one becomes the right number.

## Which bounds shrink, and why more than one

A file part spends exactly one bound: the bytes read into the seal. A table slice spends two, and both have to give. `table_chunk_bytes` caps only what is *rendered*, escaped and sealed; the rows themselves are materialised in memory by `$wpdb->get_results()` under `table_chunk_rows` alone, which is the half a memory kill is likeliest to have happened in. Halving the byte budget while leaving the fetch exactly as large as the one that just died is an adaptation that reads as one and measurably is not: it burns another whole attempt window at the same real size, and repeats that all the way to the floor. So a table stall halves both, each down to its own floor, and the slice is at the floor only when both are.

Only the bounds the failing chunk consults shrink. A structure-only table and the sealed index spend none, so those stalls have nothing to adapt and fail immediately.

## Why automatic, and why not every failure

Whether resume is automatic or operator-initiated is a real design question. Automatic risks an invisible infinite retry. Operator-initiated needs a REST verb and a client that knows to call it. This change must not touch the REST contract or the container format — the two repositories share a verified API-version ceiling — so there is no new verb, and the installed skills do not change.

The existing tick path and the watchdog are therefore the trigger. A status poll is deliberately not: `continue_after_response()` still ignores anything past `running`, so a client reading a failed job cannot accidentally revive it. The watchdog already walks every job on disk, including ones `GET /extractions` does not list.

What automatic resume is *for* is narrower than "any diagnosed stall", and saying so precisely is what keeps the promise keepable. Three conditions bound it, and the second is the one worth reading twice.

An unexpected throw stays failed and is never re-driven: its `error` is null (the message is never captured, because it could carry a path or a fragment of SQL), and that absence is the signal. Resuming a permanent bug — a file that changed mid-build, a path that no longer resolves — would loop forever.

A stall *this* release recorded stays failed too. This follows from the adaptation above rather than from a separate policy: a stall never fails the job while its bounds can still shrink, so the only stall that reaches `failed` here is one already at the floor, and re-driving it re-runs a search whose every remaining step has been tried. The two conditions are therefore mutually exclusive by construction, and a predicate admitting both would be unsatisfiable — a resume path that could never fire, defended by tests asserting a state the code cannot produce. The condition that is actually reachable is the *absence* of the schema-8 budget keys: a record whose budgets have never been adapted at all, which is precisely what 0.5.1 and earlier wrote. It is self-limiting, because the resume persists adapted budgets *and stamps those keys present*, so a second failure of the same job is no longer resumable.

Re-entering `running` occupies the concurrency slot again. A failed job frees that slot, and a new `POST /extractions` may already have taken it. The resume honours the same `max_active_jobs` ceiling the create path does — one ceiling, resolved once in `Job_Store::has_free_slot()`, because a ceiling defined once per caller eventually differs between them. The per-job tick lock cannot serialise a resume against a create for a *different* job, so the resume commits the transition, re-reads the live job set, and restores the failure verbatim if something else claimed the slot in the window. It yields in the direction that favours the caller's explicit create over an automatic resume, and a declined resume is indistinguishable on disk from one never attempted.

## Why the budget lives on the job

The chunk bounds were Config knobs, process-wide. A constant chosen without measuring the host is what killed the production run: `DEFAULT_CHUNK_SIZE` is 8 MiB, the host packaged 28,021 files none of which needed a part that large, and then died three times at byte 0 of the first file that did. Picking a smaller constant would repeat the mistake. The attempt counter is the measurement. Persisting the adapted sizes on the job — `chunk_size`, `table_chunk_bytes` and `table_chunk_rows`, zero meaning "use the Config default" — is what makes the next tick, and a resume after the job has left `running`, package the size that survived rather than rediscovering the ceiling. The record's schema version goes to 8. An older record parses unchanged: an absent budget reads as zero, which is also the signal that identifies it as resumable.

The failing unit is the *chunk*, not the file. Every file at or above the current part size stresses the host identically, so the adaptation is on the part size, never on a sort of the selection.

## Consequences

- A host whose real ceiling sits between 3.87 MB and 8 MiB — unmeasured, and not explained by either reported limit — calibrates itself on the first file that finds the wall, and the 28,021 files already packaged are kept.
- Halving is a slow search, and deliberately so: it is the only measurement available, and each step costs a full attempt window. From 8 MiB to the floor is 23 halvings at `max_stall_attempts` apiece, so a host that kills chunks for a reason size cannot fix takes hours to give up rather than minutes. What bounds that is not the floor but the sweep's absolute lifetime ceiling ([0004](./0004-background-job-and-one-time-download-link.md)), which is measured from the last real progress and is unaffected by an adapting job's heartbeat. That is the backstop; the floor is the diagnosis.
- The adapted budgets never grow back. One hostile chunk lowers the size for the rest of the job, which costs little where most chunks are far under it and is the conservative direction to be wrong in.
- A job stranded by an earlier release completes from where it stopped, once the watchdog or a further tick reaches it. An opaque failure does not, and neither does a stall this release already adapted around.
- `failed` remains a terminal state for every purpose that counts one — it frees the concurrency slot — yet is no longer strictly one-way. That is the narrow exception this decision buys, and it is confined to a record no release still in service writes. The TTL sweep is where that exception is paid for: it now reclaims a failed record on the same two windows as any unfinished job, and spares exactly the pre-adaptation stall, because that record is the resume and is older than any TTL by construction. The spare is the *absence* of the schema-8 budget keys, not their being zero: this release always writes them, so a structure-only or index stall that never shrinks is reclaimed like any other failure. `Extraction_Job::is_pre_adaptation_stall()` is the one definition both the resume and the sweep read, so the sweep can never delete a container the resume is waiting for.
- The stall bound is still a bound on retries at a given size, not a diagnosis. It cannot tell which host limit did the killing. The two-pair reason is what can: equal pairs mean the host refused the raise, differing pairs mean the raise was granted and the kill came from above PHP. That pair is the first tick's measurement, persisted on the job, so a later tick that writes the failure still describes the limits in force when the chunk died rather than whatever the current process is running under. Adaptation removes the need for the operator to guess a new constant; the floor is what still asks them to raise the host limits.
- The REST API is unchanged and its version stays 6. The poll still reports `failed` with a reason when the floor is hit, and still omits failed jobs from `GET /extractions`. No client has a new verb to learn.
- A job this release fails discards its in-progress container and sidecar at the moment it fails, keeping only the small record a poll still reads. `GET /extractions` still omits failed jobs, so the stranded-job sweep built on that listing could never reclaim them; deleting the residue at fail-time is what empties the staging a later clone would otherwise select. A pre-adaptation stall — diagnosed, no schema-8 budget keys — keeps its staging, because that is the resume. What the fail-time discard leaves behind is the record itself, and `job.json` still carries the whole selection; the sweep above is what bounds that, so a failed run is residue for one TTL rather than until uninstall.
- The sealed container's wire format is untouched.
- A table slice's row budget now binds all the way to one row. It was rounded up to a whole `INSERT` batch before use, so every value from 1 to 100 fetched 100 rows: the half of the adaptation this decision identifies as the likeliest site of a memory kill stopped adapting at a hundred rows while continuing to halve, spending roughly seven further halvings and fourteen host kills on a bound that no longer moved. The rounding now goes down and is dropped below one batch, so the slice is at the floor when the decision says it is.
- Because the exemption has no expiry, it keeps a whole cluster reachable together, not just the record it spares: `Sweeper::reclaimable()`'s carve-out, `Extraction_Job::is_pre_adaptation_stall()`, `Dispatcher::resume_failed()` (the resume path that reads it), `Sealed_Writer::seed_index()` and its call in `Artifact_Builder::advance()`, `Build_Progress::$legacy_names`, and every `from_array()` branch whose absent key is *exclusively* a signal that a record predates 0.6.0 — the schema-8 budget keys, the schema-6 `segment_names`/`table_offset`/`table_cursor` triad, the schema-6 `attempts`/`error` pair, and the schema-3/4/5 fields older still. A few other tolerant branches in `from_array()` — `progress`, `progressed_at`, and the later, still-unreleased schema-8 additions (`host_memory_limit` and its three siblings, `skipped_files`, `attempt_log`) — read an absent key as the ordinary not-yet-populated shape of a brand-new, current-schema record as much as a legacy one, so they are not part of this cluster and do not retire on this condition. The condition that retires the rest is, in shape, that no un-resumed pre-adaptation stall remains on any site still running this plugin — but nothing the plugin can observe establishes that in general: it ships to sites the author does not operate, and a site freezes the exempted record indefinitely just by deactivating the plugin (which clears both the sweep and the watchdog, per `Installer::deactivate()`) or by running with WP-Cron disabled and no replacement, with no channel back to the author either way. The condition is therefore uncheckable in general as stated; making it checkable would mean giving the exemption itself an expiry, a behaviour change this decision does not make. Removing any one piece of the cluster ahead of the others — rather than all of it, at once, once the condition holds — would make a site mid-upgrade's stranded build unrecoverable, which is exactly what this decision built the resume path to prevent.
- **Giving the exemption an expiry is a conditional follow-up, not an open recommendation** (settled 2026-08-16). The bullet above ends by naming an expiry as what would make the retirement condition checkable, and an unimplemented recommendation sitting in a Consequences list is the shape that quietly becomes permanent. It is deliberately not built, for two reasons that hold today. It is a behaviour change in the adaptation family, and nothing in that family — the host-limit raise, budget halving, the attempt counter, the floor — is built before the outstanding per-chunk measurement lands, because the measurement is expected to *delete* items in that family rather than add to them. And any expiry would be a chosen constant, not a measured one: neither a release count nor a calendar window is derivable from anything this plugin can observe, and a calendar expiry additionally depends on the very WP-Cron the freezing case has already turned off. **The trigger that would make it worth building**: an actual site is observed carrying an un-retired pre-adaptation stall long enough that the back-compatibility cluster's cost is felt — a change blocked by it, or a defect traced to one of its branches. Until then the correct action is none, and the cluster stays reachable as one piece.
