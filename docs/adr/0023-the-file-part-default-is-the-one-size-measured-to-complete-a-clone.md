# The file-part default is the one size measured to complete a clone, not the one measured to be best

`DEFAULT_CHUNK_SIZE`, the bytes of a file packaged into one bounded part when no knob overrides it, is **256 KB (262,144 bytes)**. It was 8 MiB, and 8 MiB was never measured: it was a chosen round number, and [0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md) already recorded that of 28,021 files packaged successfully on the production host the largest was 3.87 MB, so no part anywhere near the shipped default had ever actually been produced on that host. The first file large enough to need one killed a run.

`docs/measurements/2026-08-19-chunk-size-curve.md` is the controlled experiment that replaced the guess with a number. One 36 MB file, one host, one build; four sizes across five fresh single-file extractions (256 KB was run twice), under ten minutes per point, with only the size varied and every run's part count checked against it. Per-part cost grows roughly twice as fast as the part up to 2 MiB — 256 KB packages the file in 85 s, 1 MiB in 108 s, 2 MiB in 184 s, none of them retrying — and then something breaks: at 4 MiB the same file managed two parts in twelve minutes and was abandoned, about 26× the per-part cost of 2 MiB. `docs/measurements/2026-08-19-successful-run.md` then took the smallest measured value into production against the same site, the same build and the same selection that had died at 97.8 % after six hours, with `chunk_size` as the only deliberate difference: **48,578 of 48,578 files, 186 of 186 tables, 3.56 h**, pauses of 60 s or more down from 42 % of the file phase to 2.5 %.

That is the whole of the case, and it is a narrower case than "we picked the best number".

## What 256 KB is, and what it is not

**It is the only value this project has watched complete a real clone.** At 8 MiB neither production run finished: the first died at byte 0 of the first file large enough to need a full-size part, and the second — with the stall rule adapting the part down to 4 MiB — spent 44 % of six hours on three files and then died at 97.8 % of something else entirely, an opaque throw this decision neither addresses nor claims credit for (#25, #31). Every other size the project has any figure for was measured on one 36 MB file for under ten minutes. That is the ground the choice stands on: not that 256 KB is fastest in principle, but that it is the size a full extraction of 48,578 files and 186 tables has actually been carried to `ready` at.

**It is not optimal, and this decision does not claim it is.** The measurement says so in its own "What this does not establish": nothing below 256 KB was tested, and the curve's shape — per-part cost growing about twice as fast as the part all the way down the measured range — suggests smaller may well be faster still, up to the point where per-chunk overhead starts to dominate. Where that point is, these numbers do not resolve, because the experiment never went looking for it. A future maintainer who wants a smaller default must measure below 256 KB first; the shape of the curve is a reason to look, never a licence to extrapolate.

**It does not generalise to another host, and the default is not what answers that.** Every figure in both measurements is one site — LiteSpeed, PHP 8.4.21, one filesystem, one process manager. The right value is host-specific, and a shipped constant cannot be host-specific by construction. What actually answers host-specificity is the per-run `chunk_size` parameter on the create payload, which is #28's decision and not this one. Wherever that parameter is not available to the caller, the only levers are the `KNTNT_EXTRACTOR_CHUNK_SIZE` constant and the `kntnt_extractor_config_chunk_size` filter, which means editing code on production to change one number. **This decision improves the number a host starts from. It does not make the number right for that host, and it is not a substitute for the per-run parameter.**

**The 2–4 MiB threshold is still unidentified.** The experiment located it between two measured points and explained nothing about it; `php://temp`, whose 2 MB spill threshold would have been an elegant fit, was removed from `classes/` by plan 006 and is structurally absent, so it is not the cause. Bisecting and explaining it is open work (#29). 256 KB sits eight times below the lower bracket of a threshold nobody understands, which is a margin rather than an explanation, and is stated here as such.

## Why the default moves at all, rather than only the documentation

[0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md) built the adaptation family precisely so a bad constant would not be fatal: a chunk begun repeatedly and never finished halves its budget and the run continues. That machinery worked — the failed run's `attempts` series shows parts of 4 MiB, exactly half the old default, so a stall was detected and the size was halved. It still is not enough on its own, and the measurement is what makes the reason concrete.

Halving is a search that costs a full execution-time limit per attempt, and it only starts once a file large enough to need a full-size part is reached. On the failed run that was 44 % of a six-hour wall clock spent on three files out of 48,559. And the size it halved *to* was 4 MiB, which the curve now shows is already past the threshold — so the adaptation landed on a value that packages a part in about 270 s, kept the job alive, and left the run crawling. A default the host cannot survive is not made safe by a mechanism that recovers from it slowly; it is made survivable, at a price the measurement can now name.

## What is deliberately not changed

**`DEFAULT_TABLE_CHUNK_BYTES` stays at 4 MiB.** [0013](./0013-tables-are-dumped-in-keyset-paginated-slices-across-ticks.md)'s addendum derived that figure as "deliberately half the file-part `chunk_size`", on the reasoning that a host packaging 8 MiB file parts without complaint demonstrably survives that much segment payload. **That premise is now measured false** — the host did not package 8 MiB parts without complaint, it was never asked to until the run that died — so the derivation is void and the 4 MiB figure no longer follows from anything. It is kept anyway, because the alternative is worse: nothing has measured the table side at all, a table slice is a different cost from a file part (fetched as PHP row arrays, escaped into SQL, copied again through the seal), and the one production clone that completed took all 186 of its tables at exactly this value. Halving it to preserve a ratio would be inference dressed as evidence, in the direction rule R4 exists to forbid. The figure now stands on its own, unmeasured and stated as unmeasured; measuring the table side is its own experiment and its own decision.

**`max_stall_attempts` stays at 2.** Its rationale in [0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md) counted the halvings from the default to the floor — 23, from 8 MiB. From 256 KB it is 18. The argument that set the number is untouched; only its arithmetic moved, and the docblock now says 18.

**`API_VERSION` does not move, and nothing joins `HONOURED_BEHAVIOURS`.** Under [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md) the integer bounds the artifact's shape, and a smaller default changes no framing, no segment structure, no index, and no reassembly rule — a client concatenating every segment carrying a name, in index order, reads a container built at either size identically. Under [0018](./0018-a-defines-value-discloses-only-from-an-allow-list-with-a-per-record-discriminator.md)'s narrower second ground the integer moves when an already-shipped client's existing logic becomes unsafe undetectably, and nothing here does that either: a client sees more segments per large file, which is the case it has always had to handle. Nor is there anything for `honours` to announce — this is not a behaviour a caller opts into or needs to discover, it is a number the server starts from. The behaviour a client will want to discover is `chunk_size` on the create payload, and that belongs to #28.

## Consequences

- A large file is packaged in 32× as many parts as before, each carrying 32× less. On the one host measured that is a strict improvement at every point of the curve; on an unmeasured host it is a change in both directions at once — smaller parts, more of them — and per-chunk overhead is the cost that grows.
- **Every site's default packaging behaviour changes on upgrade, including sites that were not failing.** A site whose host was comfortable at 8 MiB now does more, smaller ticks for the same file and pays whatever this project's per-chunk overhead is on its host, which the successful run measured at ~229 ms and could not attribute. Such a site raises `KNTNT_EXTRACTOR_CHUNK_SIZE` back, and should measure rather than guess when it does — the method is in `docs/measurements/2026-08-19-chunk-size-curve.md` and took under ten minutes per point.
- An in-flight job that already persisted an adapted `chunk_size` keeps it: a positive per-job budget still wins over the Config default ([0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md)), so upgrading mid-run does not enlarge a part on a job that already shrank one.
- The stall reason still names `KNTNT_EXTRACTOR_CHUNK_SIZE` as the file-side knob to lower, and the halving path to the floor is now 18 attempts rather than 23.
- `tests/Integration/chunk-size-default-test.php` pins the three shipped bounds through `Artifact_Builder::budgets()`, so the file-part figure cannot drift silently back to a chosen number and the two table bounds cannot drift at all without someone deciding to move them.
- **Retiring the operator snippet that keeps production alive (#32) is what a safe default is for**, and 256 KB is the value that host needed. Whether the snippet actually goes is #32's own step, and nothing here has been run against production — this decision makes the removal possible, it does not perform or verify it.
- The right value stays host-specific and unanswerable by any default. #28 (`chunk_size` on the create payload) is what closes that, and #29 (bisecting the 2–4 MiB threshold) is what would explain the wall this margin is measured against rather than merely keeping clear of it.
