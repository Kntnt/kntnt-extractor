# Two additive caps bound what one unauthenticated `POST /extractions` costs, not how often it can be paid

`POST /extractions` let an unauthenticated caller provoke unbounded server work. Its `permission_callback`, `can_create()`, runs `validate_payload()` in full before it calls `Authorizer::authorize()`, and that method does a `realpath()` on every selected file path and two `SHOW TABLES` queries against the site's catalog. The route registered no `args` schema at all, so nothing bounded how many entries `tables`, `tables_structure_only`, or `files` could carry, and nothing bounded the raw body's size either. Because `Authorizer::authorize()` is also the first and only place in this path that calls `is_user_logged_in()` or `current_user_can()` — and therefore the first thing that forces WordPress to resolve an identity at all — the work was not merely pre-*authorization* for a caller with bad credentials, it was pre-*authentication* for a caller with none. Anyone who could reach the endpoint could spend the site's CPU and filesystem I/O in proportion to a number they chose, and be told "401" only after it had been spent.

`POST /extractions` now refuses a raw body over `max_body_bytes` with `413 kntnt_extractor_payload_too_large`, before `json_decode()` is called on it, and a combined `tables` + `tables_structure_only` + `files` selection over `max_selection_elements` with `422 kntnt_extractor_selection_too_large`, as soon as the three arrays' shape is settled and before any element of one reaches a `realpath()` call or the table catalog. Both resolve through the Config seam, so a site raises either with a `wp-config.php` constant or the matching filter. Both refusals carry the limit they were checked against and the caller's own size — `bytes` or `count` — in the error's `data`, so a client that is refused can split or shrink its request from the one response rather than probing for the boundary.

## The caps are prepended to the ladder, never woven into it

[0003](./0003-generic-manifest-and-table-list-no-server-side-categorisation.md) settled the order the create request is validated in, and this decision does not reopen one line of it: a resource name that does not already exist is still rejected before any capability check runs, and the 404 still names every offender. `plans/README.md` records that ordering under "Findings considered and rejected" precisely so it is not re-audited, and carves out the half that was still open — the unbounded work, no schema, no element cap, no body-size cap. This decision closes that half and touches nothing else. The two caps run *ahead of* every check the ladder orders — the shape checks, the overlap check, the `strict` check, the public-key check, `Restricted_Path::matches()`, `missing_tables()` and `classify_files()` — rather than between any two of them, so a request inside both caps is validated in exactly the sequence [0003](./0003-generic-manifest-and-table-list-no-server-side-categorisation.md) fixed, in exactly the order it fixed it. The integration suite pins that directly: every pre-existing assertion in `tests/Integration/extractions-test.php` still passes verbatim, and a new one sends a body of exactly the cap and watches it run the whole ladder down to the capability gate.

Neither cap is an existence oracle. They are content-shape checks on a count and a byte length; they carry no information about whether any particular table or file exists, and they refuse identically whatever was selected. [0012](./0012-identity-dependent-responses-are-never-cacheable.md)'s uniform-refusal discipline is therefore untouched, as is `resolve_owned_job()` and the id-addressed routes it governs.

## Why manual checks rather than a REST `args` schema

The obvious mechanism — declaring `tables`, `tables_structure_only` and `files` in the route's `args` with a `maxItems` — was rejected. WordPress validates a route's `args` schema before the `permission_callback`, which is earlier than either cap needs to be, but it also takes over the refusal: a shape core's own `rest_validate_value_from_schema()` rejects comes back as a generic `400 rest_invalid_param`, not as the precise, ordered code this endpoint's contract promises. A non-array `tables` is `422 kntnt_extractor_malformed_body` today and is pinned as such by the suite; introducing a schema for these three members would have silently reclassified that case, and every other in-cap malformed shape with it, to buy an earlier position the manual check does not actually need. Both caps are therefore ordinary checks inside `validate_payload()`, written like every other check in it. That the checks read the raw body rather than a parsed parameter is what makes the body cap possible at all — it has to see the string before `json_decode()` does.

## The numbers are measured, not chosen

A real production run of `safeteam.se` selected **186 tables and 49,116 files**, 2.23 GB ([0014](./0014-the-persisted-record-is-split-so-a-save-is-bounded.md)); `README.md`'s own worked example of a poll response uses the same order of magnitude. That is the one real selection size this project has evidence for, and it is a legitimate clone — the job this plugin exists to do. A synthetic payload built to the same shape — 186 table names and 49,116 file paths, with path samples deliberately longer than the real run's, encoded exactly as the endpoint expects — measures **4,687,437 bytes (4.47 MiB) for 49,302 combined elements**. `DEFAULT_MAX_SELECTION_ELEMENTS = 500_000` is about 10.1× that element count and `DEFAULT_MAX_BODY_BYTES = 52_428_800` (50 MiB) about 11.7× that byte count, so a site an order of magnitude larger than the only one measured still clears both.

They are two knobs rather than one because they bound two different costs. Element count bounds the number of `realpath()` calls and catalog comparisons; body size bounds `json_decode()`'s CPU and memory for a body that could carry very few elements made of enormous individual strings, and would pass any count. Collapsing them would leave one of the two costs unbounded.

## What this does not fix

**The caps turn unbounded pre-authorization work into large-but-finite pre-authorization work. They do not make that work small.** At the default element cap a single uncredentialled request may still put 500,000 entries in `files` and force a `realpath()` on every one of them before `Authorizer::authorize()` is ever reached. [0014](./0014-the-persisted-record-is-split-so-a-save-is-bounded.md) measured filesystem calls on this project's own investigated hosts as ranging from cheap on a fast local disk to a few milliseconds each on a networked or overlay filesystem; at a few milliseconds a call, half a million calls is on the order of *minutes* of single-request filesystem work, not seconds. A selection weighted toward tables instead is cheaper per element — two fixed `SHOW TABLES` queries and an in-memory scan against a few hundred real names — but the combined cap permits that weighting too, and scanning up to 500,000 requested names against a few hundred real ones is still hundreds of millions of string comparisons. The operation the finding names is capped, not removed.

**Repetition is untouched, deliberately.** Nothing here stops the same caller from sending that same near-cap request again immediately, or many callers from sending it at once. These caps bound the cost of *one* request and say nothing about the rate requests arrive at. The mitigation for repetition is rate limiting — a web-server, WAF, or hosting-layer control — and this plugin has no seam for it today and does not gain one here. It is named as unimplemented rather than left unsaid, because a reader who sees only the caps will conclude the pre-authorization cost problem is solved, and it is only bounded per request.

**The cap sits at 500,000 rather than lower because of the margin it was chosen against.** The alternative is a cap that refuses the 49,302-element production selection this plugin measurably exists to serve, or leaves it too little headroom to survive a site's growth. A plugin that reliably declines the one large legitimate job it was built for is a worse failure for this project's actual users than a bounded, finite amount of pre-authorization work is for its threat model. That is a stated trade, not an oversight. A future maintainer who wants the cap lower should re-derive it against a larger measured production selection first, not guess at a smaller number and assume it is safe.

**The body cap bounds decoding, not the read.** WordPress core reads the entire raw request body into `WP_REST_Request` before any plugin code runs, this route's `permission_callback` included, so nothing here executes early enough to refuse a request before that read. A caller who wants to exhaust memory purely by sending a body larger than `memory_limit` still can, bounded only by the web server's `client_max_body_size` and PHP's `memory_limit`/`post_max_size` — infrastructure this plugin does not control.

## Why this does not move `API_VERSION`

Under [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md), `API_VERSION` bounds the *artifact's* shape, and nothing here changes a byte of it: no framing, no segment, no index, no reassembly order. Under [0018](./0018-a-defines-value-discloses-only-from-an-allow-list-with-a-per-record-discriminator.md)'s narrower second ground, the integer also moves when an already-shipped client's existing behaviour would become unsafe against the new server undetectably and without its consent — and that does not apply either. The caps refuse a request no real client sends, with two new error codes on an endpoint every client already has to handle errors from; an old client that never hears of `selection_limits` is unaffected until it sends a selection ten times larger than any measured one, and then it is refused loudly and told the number. That is the additive shape `honours` exists for, so `selection_limits` is named in `Status_Controller::HONOURED_BEHAVIOURS` and `API_VERSION` stays `7`.

`honours` is presence-only by design, so the name can only ever tell a client that some cap exists, never what it is — which is why both refusals carry their own `limit`. That is where a client needs the number anyway: at the moment it must split a request, not in advance of ever sending one.

## Consequences

- `POST /extractions` gains two refusals, both ordered ahead of every existing check and ahead of the capability gate: `413 kntnt_extractor_payload_too_large` for a raw body over `max_body_bytes`, and `422 kntnt_extractor_selection_too_large` for a combined selection over `max_selection_elements`.
- Each refusal's `data` carries the `limit` it was checked against alongside the caller's own `bytes` or `count`, so a client can act on the number without a second call.
- Both caps are Config knobs — `KNTNT_EXTRACTOR_MAX_SELECTION_ELEMENTS` / `KNTNT_EXTRACTOR_MAX_BODY_BYTES` and their `kntnt_extractor_config_*` filters — clamped to a floor of one, so a misconfigured knob cannot disable the endpoint's own contract. `Extractions_Controller` reads the Config seam again as a result; the concurrency ceiling is still not among what it reads.
- A request inside both caps is validated in exactly the order [0003](./0003-generic-manifest-and-table-list-no-server-side-categorisation.md) fixed. The 404-before-403 ordering is unchanged and stays settled.
- `selection_limits` joins `Status_Controller::HONOURED_BEHAVIOURS`; `API_VERSION` stays `7` and no coordinated release is required.
- **The finding is bounded, not closed.** One unauthenticated request can still cost minutes of filesystem work at the default cap, and the rate at which such requests arrive is not addressed here at all. Rate limiting remains unimplemented and belongs to the hosting layer. Do not read the caps as making pre-authorization work cheap.
- **If a real site's legitimate clone is ever refused by either cap**, raise that site's constant or filter. It is not a signal to remove the cap, and lowering either default needs a fresh measurement of a real production selection first.
