# `api_version` bounds the artifact contract; a new authenticated `honours` list reports what a build actually does

`api_version` has been asked to answer two different questions at once, and it cannot. The first is "may I proceed at all with this artifact contract?" — the consuming client's verified ceiling, checked before anything else, because getting this wrong is not theoretical: version 5 changed a table's sealed-index entry from one segment to one-or-more, and a client built against an older shape kept only the last slice of a multi-segment table and lost data silently, with no error to notice. The second is "what does this build actually do?" — and the integer cannot answer it, provably. `strict: false` on `POST /extractions` (`classes/Rest/Extractions_Controller.php:772`) shipped while `API_VERSION` stayed `6`, on the reasoning [0005](./0005-github-releases-self-hosted-update-checker.md) itself states: additive, and the default is today's behaviour, so an old client is unaffected. That reasoning is sound about compatibility and fatal to inference — it means no version number will ever distinguish an Extractor that honours `strict` from one that ignores it, not now and not retroactively. A caller that wants to use it has no way to find out short of trying, and a caller that assumes it works gets a hard failure on the first vanished file instead of the reported skip it asked for.

This amends [0005](./0005-github-releases-self-hosted-update-checker.md), whose own words are broader than what now governs: "increments only when caller-visible behaviour changes, including a purely behavioural change with no signature change." `CONTEXT.md`'s **API version** entry currently repeats that reading. Both are narrowed by this decision. `API_VERSION` no longer means "any caller-visible change, however small"; it means the artifact's shape — the container's framing, segments per resource, the sealed index, and reassembly order. `strict` was never that, which is exactly why it could ship without moving the integer in the first place: the practice was already ahead of the stated rule, and this ADR is where the rule catches up rather than staying silent about the gap.

## The fix: two questions, two mechanisms

Keep the integer for the artifact contract and the ceiling — the question a client must answer before it trusts anything the container claims about its own shape. Add `honours`, a named list of behaviour strings, for everything else. A capability joins the list the moment it ships, whether or not `API_VERSION` moves that release, and nothing is ever inferred from the number that the number was never built to carry.

**The split is anonymous integer, authenticated list, and both halves are load-bearing.** `api_version` stays exactly where [0005](./0005-github-releases-self-hosted-update-checker.md) put it: unauthenticated, because the consuming client's health check reads it before resolving any credential, precisely so a wrong-version server is refused on the cheapest possible call. Moving it behind a gate would make a broken Application Password indistinguishable from an incompatible server — the health check exists to keep those two failures apart. `honours` goes inside `is_user_logged_in()` in `classes/Rest/Status_Controller.php:get_status()`, alongside the identity report [0012](./0012-identity-dependent-responses-are-never-cacheable.md) already added there. The consuming client's every use of a behaviour-gating name is already post-authentication — `strict` on the create call, `chunks_done` in an authenticated poll loop — so nothing needs the list before credentials resolve, and the list is a build fingerprint, which an anonymous caller does not need handed to it for free.

## The blind spot this addresses

The versioning rule as practiced reasons in one direction only: old-client-against-new-server, where "additive, and the default is current behaviour" keeps an unaware client working. It has never reasoned about the other direction — new-client-against-old-server — and that is the direction that has actually bitten in production, which runs a release two versions behind. A client that has learned to expect `strict` has no signal, short of trying it and getting a plain hard failure, that the server it is actually talking to predates it. `honours` closes exactly that gap: a client checks for a name before depending on it, in either direction, instead of assuming its own vintage is also the server's.

## Consequences

- An unknown name in `honours` is forward-compatible noise: a client should ignore any name it does not recognise, the same tolerance it already extends to unknown response keys.
- Absence is the only signal. There is no boolean map and no "false" entry — a capability not implemented is simply not in the list — so the list must stay complete. A behaviour that ships without being named here is the `strict` failure again, one layer up, and is now a maintenance error rather than an inherent limit.
- Adding a capability to `honours` is additive by construction and never moves `API_VERSION`. If a REST-only change ever seems to need the integer bumped, that is a signal this ADR needs revisiting, not a signal to bump.
- `API_VERSION` moves only when the artifact's shape moves: the container's framing, segments per resource, the sealed index, or reassembly order. A behavioural change to a request or response field, however caller-visible, is a `honours` entry instead.
- `CONTEXT.md`'s **API version** entry is updated to match this narrower reading.
