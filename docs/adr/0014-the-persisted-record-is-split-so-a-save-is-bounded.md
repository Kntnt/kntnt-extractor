# The persisted job record is split so that a save costs the same whatever the selection

A job's record is persisted as two files rather than one. `job.json` holds the selection — the requested full-data tables, structure-only tables, and files — and is written exactly once, by `Job_Store::create()`. `state.json` holds everything else and is what every save rewrites. The ordered segment names leave the record entirely: they accumulate in an append-only index sidecar beside the in-progress container, owned by `Sealed_Writer`, and the record keeps only their count and the sidecar's committed byte length. The two halves are read back together and merged into the single decoded shape `Extraction_Job::from_array()` validates, so the schema keeps one definition. The record's schema version goes to 7.

The line is drawn at what is **unbounded**, not at what is mutable. That distinction is the whole decision: several fields never change, but only three of them — `tables`, `structure_only`, `files` — grow with the caller's selection, and only one other thing in the record grew at all. Splitting on immutability would have moved a base64 key and two hex tokens out for nothing; splitting on unboundedness leaves `state.json` a fixed set of scalars, and that is a property the test suite can hold it to forever rather than a size that happens to be small today.

## The measurement that forced it

A real extraction of `safeteam.se` — 186 tables and 49,116 files, 2.23 GB — packaged every table in 261 s and then settled into **3.9–4.8 files per second**, putting the file phase alone at about 3.2 hours. That is roughly 230 ms to read, encrypt, and append a file averaging 44 KB. Encryption is not the cost: libsodium does gigabytes per second, so the whole 2.23 GB of `crypto_secretbox` is a few seconds and 49,000 `crypto_box_seal` calls a couple more. Nearly all of that 230 ms was overhead.

`Dispatcher::advance_one_chunk()` calls `Job_Store::save()` **twice per chunk** — once before the work, to count the attempt and refresh the heartbeat ([0013](./0013-tables-are-dumped-in-keyset-paginated-slices-across-ticks.md), [0007](./0007-pure-php-chunked-resumable-loopback-driven-extraction.md)), and once after, to persist the progress — and `Artifact_Builder::advance()` packages one file per chunk. Each of those saves re-encoded and rewrote the *entire* record: 49,116 paths that could not change, plus a `segment_names` list that grew by one entry per chunk toward 49,116 more. The state file was observed at 4,314,102 bytes on production at the start of the run and grew from there. **Two writes × 49,116 chunks × a record averaging ~6 MB is on the order of half a terabyte of JSON, written to move 2.23 GB of files.** The rate decayed measurably as the run went on, which is the signature of a per-chunk cost proportional to the build's own progress rather than of a constant overhead.

The reasoning above was checked before any of it was acted on, by running the real `Job_Store`, `Artifact_Builder` and `Sealed_Writer` over a synthetic 49,116-path selection and timing the two halves of the loop separately:

| Selection carried in the record | ms per chunk in `save()` | ms per chunk in `advance()` |
|---|---|---|
| 49,116 paths (production-sized) | 6.455 | 0.262 |
| 1,200 paths (identical work) | 0.449 | 0.214 |

The packaging work is the same in both rows — the same files, the same bytes, the same seals. Only the record's size differs, and it accounts for **96 %** of the per-chunk time in the first row. Timing `save()` alone against a growing segment list showed the decay directly: a record of 3.98 MB saved in 3.14 ms and one of 8.15 MB in 6.01 ms, linear in size, which on two saves per chunk is a throughput falling from 159 to 83 files/s on that machine for no reason but bookkeeping.

Splitting `persist()` into its encode and its write half showed something worth recording, because it changes what the fix is worth on a slow host: encoding dominates. A 4 MB record cost 2.44 ms to encode and 0.42 ms to write; an 8 MB record 5.14 ms and 1.22 ms. The cost is therefore mostly CPU spent serialising tens of thousands of strings, not disk. `JSON_PRETTY_PRINT` was dropped with the split, but for its 12–15 % of bytes rather than for time — it costs essentially nothing to produce, and nothing reads these files by eye.

## Why not the alternatives

**Save less often.** Batching the progress write across many chunks would have cut the number of saves without touching their size. It was rejected as the primary fix because it addresses the multiplier rather than the defect: a 6 MB write to move a counter is wrong at any frequency, and the record would still have grown without bound. It is also the change that widens the crash window, and it would have had to be argued for on those grounds — whereas this split changes when nothing is written and what is written, leaving *when* exactly as it was.

**Cache the encoded selection.** Keeping the immutable fragment's JSON in memory would have removed the encode cost but not the write, and it survives only within one PHP invocation. Against a ~2.5× improvement it adds a cache to a persistence seam that currently has none.

**Derive the segment names instead of storing them.** The build order is deterministic — full-data tables, then structure-only, then files in selection order — so the names look derivable from the cursor plus the selection. They are not: a table contributes one segment per slice and a large file one per part, and how many slices a table takes is not knowable until it is dumped ([0013](./0013-tables-are-dumped-in-keyset-paginated-slices-across-ticks.md)). Deriving them would mean reconstructing a number that only the dump knows. The sidecar stores what cannot be derived, at one append per segment.

**Change the container format so a segment holds many files.** Packing files into ~8 MB segments would cut 49,116 segments to about 280 and shrink the per-segment bookkeeping by the same factor. It is a caller-visible change to the artifact, so it needs an API version bump and a matching change in `kntnt-wp-skills`' reader, and it does not remove the per-file cost of `realpath`, `stat`, and `read` that any packaging must pay. It is not ruled out, but it must not be reached for before the free win is measured, and it is not what this decision does.

## The crash window, which does not move

The container is built append-only, so the reason progress is persisted after every chunk is that a tick killed between appending a segment and recording it would otherwise resume from a cursor pointing before that segment and append it twice. That reason is untouched here: the save still happens after every chunk, and the same is true of the save *before* the chunk, which exists so a tick killed outside PHP — an exhausted `memory_limit` or `max_execution_time`, where no `catch` runs — still leaves its attempt counted ([0013](./0013-tables-are-dumped-in-keyset-paginated-slices-across-ticks.md)). Both saves stay exactly where they were; they simply write a few hundred bytes instead of megabytes.

What the sidecar does add is a second file that must roll back in step with the container. It is anchored the same way: `suspend()` reports both committed lengths, `resume()` truncates both back to them, and both offsets live in the same progress record, so they are persisted together or not at all. A crash between the container append and the index append leaves one file ahead of the other, and the next resume truncates each to its own anchor, which discards exactly the uncommitted tail of both. A missing sidecar fails the build closed rather than continuing, because continuing would publish an index naming only the segments sealed after the crash — the one failure mode here that would be silent, since such a container is well-framed and opens cleanly and is simply missing most of its names.

## Consequences

- A save's cost is independent of the selection. `state.json` is 598 bytes on the production-sized fixture, and the suite holds it under a fixed ceiling across a multi-segment build rather than trusting that it stays small.
- Re-measured on the same machine and the same fixture, the per-chunk cost falls from **6.72 ms to 0.49 ms — a factor of 13.8**, of which `save()` is now 0.24 ms (two atomic writes of a few hundred bytes) and packaging the file the other half. The property matters more than the factor: the same run with a 1,200-path selection costs 0.54 ms per chunk against the 49,116-path selection's 0.49 ms, where before the split the two were 0.66 ms and 6.72 ms. Per-chunk cost no longer varies with how much was selected. The index sidecar costs nothing measurable — `advance()` is 0.25 ms before and after.
- **That factor will not carry over to a slow host, and saying so is the point.** It is the factor where `save()` was 96 % of the work. On the production run, the slope of its own decay — 22 ms per megabyte of record, from 4.75 files/s at a 4.3 MB record to 3.86 at 6.5 MB — puts `save()` at 45 % of a chunk at the start of the run and 56 % near the end. Removing it should therefore take that host from about 3.2 hours of file phase to somewhere near 1.5, a factor of roughly two, **not fourteen**.
- **Over half of that host's per-chunk time remains unexplained by anything measured here**, and closing this is worth more than anything else in this area. A chunk makes fifteen to twenty-five filesystem calls — `realpath` twice, `stat` three times, the container's own `suspend()`/`resume()` pair of opens plus a truncate and a close on a file growing past a gigabyte, and the file's own open-read-close — and at the few milliseconds each that a networked or overlay filesystem charges, that is the right order of magnitude for the residual. It is a hypothesis, not a measurement: it needs a real host to settle. If it holds, the per-chunk half of it is amortisable by sealing several segments under one open container, which needs no format change and no API bump.
- The record is schema 7. A schema-6 record written by an earlier release still parses: its `segment_names` becomes the segment count, and on the first resume after the upgrade `Sealed_Writer::seed_index()` rebuilds the sidecar from exactly those names, so an extraction hours into its run survives the upgrade rather than being abandoned or, worse, publishing a truncated index. That path exists only for records that can still be live and can be dropped once none can. **It was dropped on 2026-08-21 with the rest of ADR-0015's back-compatibility cluster (#52); a schema-6 record no longer parses at all, and is skipped rather than resumed.**
- A running job's directory now holds one more file, `<artifact>.building.names`, carrying the plaintext names of the segments sealed so far. It sits in the same deny-hardened directory as the selection it is drawn from, so it discloses nothing that was not already there, it is never published, and it is removed at finalize once those names are sealed into the container.
- The REST API is unchanged and its version stays 6. `progress.chunks_done` is still the count of committed packaging chunks and still moves once per sealed segment; it is simply read from a counter rather than from the length of a list. No client can tell the difference.
- `Sealed_Writer::resume()` and `suspend()` changed shape — the former takes two offsets instead of a name list and an offset, the latter returns both. Both are internal to the plugin; the container's wire format is untouched, so an artifact produced by this release is byte-compatible with one produced by 0.5.1 and `kntnt-wp-skills` needs no change.

## Outcome of the measurement this decision asked for (2026-08-19)

The production measurement this ADR said needed a real host was taken on 2026-08-18, on the same host that produced the original figures, against the first release carrying the split. The full record, with its raw sample series, is `docs/measurements/2026-08-18-production-run.md`. Three results bear directly on what is written above.

- **The predicted factor of two did not materialise.** With pauses removed so the comparison is like for like, the file phase ran at 3.89 files/s and 257 ms per chunk, against the prior release's 4.75 files/s and roughly 210 ms on the same host; the best sustained ten-minute window reached 179 ms. The estimate that `save()` was 45–56 % of a production chunk was wrong — it was a far smaller share. The ~115 ms this ADR could not attribute is not a residue around a known cost; it is very nearly the entire cost. **The claim this decision makes about selection-independence is untouched** — per-chunk cost no longer varies with how much was selected, which this run did not test and does not contradict. What is retracted is the prediction of what the split would buy on a slow host.
- **The dominant cost is per part, not per file, and it is enormous.** Three files large enough to need more than one part — 0.006 % of the selection — consumed 44 % of the observed wall clock, packaging at roughly 12.7 KB/s against ordinary files' 220 KB/s. Per-file path resolution and stat calls cannot explain a cost that grows with the part count, so the filesystem-latency hypothesis as this ADR framed it — fifteen to twenty-five calls per 44 KB chunk — is not what dominates. Whatever does scales with the part.
- **The run failed opaquely at 97.8 %**, with `$job->error` null and therefore no stall reason and no two-pair limit reading. The measurement that would attribute the remaining cost still cannot be made from outside the plugin, and the failure mode that actually ends runs on this host writes nothing about itself. Both are now queue items rather than open questions.

## Addendum (2026-08-21) — `job.json` is written once *and* by a tick that skipped a file

The opening paragraph says `job.json` "is written exactly once, by `Job_Store::create()`". That stopped being true when `strict: false` was widened to cover a file that vanishes during packaging ([0026](./0026-strict-false-covers-the-whole-run-and-a-partly-packaged-file-is-never-skipped.md)): the skipped path is appended to `skipped_files`, which lives in this half, so a tick that skipped something rewrites the selection file through `Job_Store::save_with_selection()`.

**The decision this ADR took is untouched, and the second paragraph is why.** The line was drawn at what is *unbounded*, deliberately and not at what is immutable, and that is exactly the distinction that lets this change cost nothing here. `save()` is unchanged and still writes `state.json` alone, so the hot path — twice per packaged chunk — is still a fixed set of scalars. The wider write is paid once per *skip*, on a run where files are disappearing under the packaging, and never once per save. A run that skips nothing never reaches it.

What the earlier sentence should have said is that no *lifecycle transition* rewrites the selection, which is still true: it is not the state machine that reaches this half but one bounded event inside packaging.
