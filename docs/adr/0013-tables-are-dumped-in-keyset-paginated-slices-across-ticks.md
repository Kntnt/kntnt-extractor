# A table is dumped in keyset-paginated slices across ticks, and a chunk that never advances fails the job

A table is packaged exactly the way an oversized file already is: in bounded chunks, one per tick, each its own independently-sealed segment recorded in the sealed index under the table's own name, so a reader reassembles a table by concatenating its segments in index order — the same rule that reassembles a file from its parts. The rows of one chunk are read by keyset pagination on the table's primary key, never with a single unbounded `SELECT *` and never with `LIMIT`/`OFFSET`. The mid-table position — how many rows are sealed, and the key tuple the next slice seeks past — joins the file byte offset in the job's persisted build progress, which raises the record's schema version to 6. Alongside it, a chunk that is begun repeatedly and never finishes stops being retried: the job is failed with a reason that names the chunk and the host limits that most likely killed it.

The previous design packaged one whole table per tick from one unbounded `$wpdb->get_results( "SELECT * FROM …" )`, materialising every row in PHP memory and then concatenating the whole data block into one string on top of that. That is fine for a small table and unsurvivable for a large one, and the failure it produced was the worst possible shape: the tick was killed by the host — an exhausted `memory_limit` or `max_execution_time`, both of which terminate the worker outright rather than raising anything PHP can catch — so the `catch` that exists to drop a failed build to `failed` never ran, the stall [0007](./0007-pure-php-chunked-resumable-loopback-driven-extraction.md) watchdog restarted the job, and the cycle repeated without bound. A polling caller saw `state: "running"` with a frozen table counter, no error, indefinitely. Measured on a production site (Extractor 0.3.0, PHP 8.4, MariaDB 11.4): a 12 MB / 2,909-row `wp_posts` completed, a 56 MB / 119,674-row `wp_relevanssi` did not advance in five minutes, and a 493 MB / 100,893-row `wp_postmeta` did not advance in forty. Because `wp_postmeta` is content and cannot be dropped from a clone, this made the site unclonable outright — and nothing about it is specific to that site: any table above whatever a given host's ceiling happens to be was unextractable.

Keyset pagination is chosen over `LIMIT`/`OFFSET` because an offset walk re-reads and discards every row it has already passed, so the cost of the *n*th page grows with *n* and the total dump is quadratic — on precisely the tables that forced this decision. Seeking past the last key tuple instead uses the primary-key index directly and costs the same for the first page and the thousandth. The seek predicate is written as the lexicographic expansion `(k1 > v1) OR (k1 = v1 AND k2 > v2) OR …` rather than as the row-value comparison MySQL also understands, because the expansion is ordinary SQL that survives any engine or translation layer `$wpdb` sits on and collapses to a single term for the ordinary one-column key.

Not every table has a single-column primary key, and the design does not assume an `ID` column exists — it asks the engine. `SHOW KEYS` yields the primary key's columns in the index's own `Seq_in_index` order, and the whole tuple is used, so a composite primary key is paged exactly like a simple one rather than being pushed onto a fallback; WordPress core itself ships one, on `wp_term_relationships`. Primary-key columns are `NOT NULL` by definition, which is what lets the predicate be a plain comparison with no null handling. A table with no primary key at all — a plugin table occasionally has none — falls back to a `LIMIT`/`OFFSET` walk with no `ORDER BY`. Adding an ordering there was considered and rejected: the only totally-ordering expression available on such a table is every column at once, and sorting an unindexed table on all of its columns would force a full filesort for every page, which is strictly worse than the offset scan it would replace on exactly the large tables this exists for. The unordered walk assumes only that the engine returns an unmodified table in a stable order — the same assumption `mysqldump`'s own single unordered scan makes — and no dump here is transactional in any case. Falling back to a unique index instead of the primary key was considered and rejected as complexity without a demonstrated case: a unique index may admit nulls, and no table encountered so far has one without also having a primary key.

Slices are cut on extended-`INSERT` boundaries, by rounding the row budget up to a whole number of statement batches. That is what makes the emitted SQL byte-identical however the budget is tuned, and it is why a table resumed across twenty ticks and the same table dumped in one call produce the same bytes: chunking changes where the SQL is cut and nothing else. The budget is a row count rather than a byte count (`table_chunk_rows`, default 1,000) because rows are what the query itself is bounded by; a site whose rows are unusually fat lowers the knob rather than discovering the host's ceiling by being killed at it. It is deliberately a knob of its own rather than a reuse of the file `chunk_size`, since the two bound different things and a site has no reason to move them together. **This paragraph's central claim was wrong in the field and is superseded by the addendum below.**

Making a repeatedly-dying tick surface as `failed` reuses the machinery `progressed_at` already established rather than adding a parallel one. A counter on the job record is incremented immediately *before* a chunk runs and persisted at once — which is the entire point, since a chunk killed outside PHP leaves nothing behind that runs afterwards — and is cleared by the same transition that stamps `progressed_at`, so it always counts consecutive attempts since the last real advance. Once it reaches the bound (`max_stall_attempts`, default 3) the driver fails the job. Deriving the stall from `progressed_at` alone was considered and rejected: a wall-clock threshold cannot distinguish a chunk that has been begun three times and killed three times from one that is legitimately slow, whereas counting begun-but-unfinished attempts can, and it needs no threshold tuned per host. The [0007](./0007-pure-php-chunked-resumable-loopback-driven-extraction.md) sweep's absolute lifetime ceiling is unchanged and stays the coarser outer backstop for a job that never reaches the driver at all.

The failure reason is caller-visible, which is a narrowing of the opacity the tick's `catch` keeps. That catch stays opaque — an unexpected throw's message can carry a filesystem path or a fragment of SQL and is still never captured — but the stall is a failure the plugin diagnoses itself and can describe safely, from the caller's own selection plus two runtime settings `GET /environment` already discloses to the same capability. It has to be usable, because the host that produced this failure mode had `WP_DEBUG` and `WP_DEBUG_LOG` both off and left no log at all: the message therefore names how many attempts died, which table and row (or file and byte) they died on, and the host's `memory_limit` and `max_execution_time`, so the next occurrence explains itself without server access.

## Consequences

- A table of any size completes, across as many ticks as it takes, on any host whose per-request budget fits one slice. The per-tick working set is one slice of rows and its ciphertext, not a whole table.
- A table now appears in the sealed index once per slice rather than once. A reader that keyed a map by segment name and kept the last value it saw will silently lose all but a table's final slice; the correct rule — concatenate every segment carrying the name, in index order — is the one file parts have always required. This is a caller-visible change to the artifact and increments the API version (see [0005](./0005-github-releases-self-hosted-update-checker.md)).
- The persisted job record is schema 6. A record written by an earlier release parses unchanged: an absent mid-table position reads as "no table mid-dump" and an absent attempt counter as zero, so an in-flight job survives the upgrade rather than being abandoned.
- Rows of a keyed table are now emitted in primary-key order, where before they came back in whatever order the engine chose. The dump reloads identically either way, but a byte-for-byte comparison against an artifact produced by an earlier release will differ.
- A job whose chunk cannot complete reaches `failed` within a few poll cycles instead of never, and its `error.message` explains why. A caller that treated `failed` as needing no further inspection now has something worth reading.
- The stall bound is a bound on retries, not a diagnosis: it cannot tell which host limit did the killing, only that something outside PHP did. The reported settings are what let a reader decide. **Superseded in part by [0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md):** a spent counter now halves the chunk's budget and continues; only a one-byte floor still fails the job.
- `max_stall_attempts` and `table_chunk_rows` join the Config knobs, both floored so a misconfiguration cannot disable the protection they exist to give.

## Addendum (2026-08-14) — a slice is bounded by bytes as well as by rows

The paragraph above reasoned that a row budget suffices because "a site whose rows are unusually fat lowers the knob rather than discovering the host's ceiling by being killed at it". A site did exactly the latter. On `safeteam.se`, `wp_rcb_template` — **726 rows, 16.31 MB, ~23 KB per row** — sat far inside the 1,000-row default, was therefore taken in a single slice, and never finished one: three consecutive attempts died where no `catch` could see them and the job was correctly failed with the stall reason this ADR added. The contrast in the same run is what shows the unit itself was wrong, not merely its value: `wp_postmeta`, at **100,890 rows and 493 MB**, went through in about a hundred slices without trouble, because a thousand narrow rows is a small slice. It is not a table's size that decides whether a slice fits, it is its rows'.

Decision: `dump_chunk()` takes a byte budget alongside the row budget (`table_chunk_bytes`, `KNTNT_EXTRACTOR_TABLE_CHUNK_BYTES` or its filter, default 4 MiB) and a slice ends at whichever bound is reached first. Four MiB is deliberately half the file-part `chunk_size`: that same host packaged 8 MiB file parts without complaint, so 8 MiB of segment payload is demonstrably survivable there, and a table slice costs more per byte than a file part — it is fetched as PHP row arrays, escaped into SQL, and copied again through the seal. **That premise was measured false and this derivation is void; see [0021](./0021-the-file-part-default-is-the-one-size-measured-to-complete-a-clone.md).** The host had never been asked for an 8 MiB part at all, and when it was, the part could not be packaged. The 4 MiB figure itself is kept — nothing has measured the table side, and the one production clone that completed took all 186 of its tables at this value — but it now stands on its own rather than on the file part's, and it stands unmeasured. **Which of the host's two limits actually broke is not known.** The plugin reports both (`memory_limit 768M`, `max_execution_time 300`) and can observe neither killing it, and measuring it would have required another production run against a site a parallel clone had claim to; the margin stands in for the measurement rather than dressing a guess up as one. A table of ordinary rows never reaches the byte bound at all — the row budget is spent long first — so this costs nothing on the tables that already worked.

The completeness rule had to change with it, and this is the subtle part. "A short page is the end of the table" was sound while rows were the only bound, and becomes **ambiguous** the moment a page can be cut short for a second reason: a short page now means either the table ran out or the byte budget did. Reading it the old way would end a table mid-row-set and seal a **silently truncated dump that reloads without a single error** — strictly worse than the loud stall it replaces, because nothing downstream would ever say so. So the fetched page and the rendered page are separated: the table is complete only when every fetched row was rendered **and** the page came back shorter than asked for, and the cursor is the last row *rendered*, never the last one fetched.

The byte cut lands on a row rather than on a statement batch, which costs the byte-identity property claimed above: while the row budget is what bounds a slice, cuts still land on batch boundaries and the emitted SQL is unchanged, but a byte-bounded slice groups its rows differently than an unsliced dump would. Batch granularity was considered and rejected — it would preserve the property, but a single batch of a hundred fat rows can overshoot the budget many times over, which is the exact failure this bound exists to prevent. What every consumer actually depends on is preserved: a slice always ends on a complete statement, so the concatenation is valid SQL however the slices fell. Every slice also renders at least one row even when that row alone exceeds the budget, since a slice that rendered nothing would advance no cursor and stall the build on a row it could never fit.

### Consequences

- A table of few fat rows completes rather than failing the job. The row budget remains the coarser bound and the one that governs how much is READ; the byte budget governs how much is rendered and sealed.
- A byte-bounded slice's SQL is equivalent to, but not byte-identical with, the same table dumped in one call. Consumers may assume a complete statement per slice and nothing more; `kntnt-wp-skills`' container-format contract states it in those terms.
- `table_chunk_bytes` joins the Config knobs, floored at one byte so a misconfiguration cannot disable the bound — at the floor the build advances one row per slice rather than stopping.
- The stall reason names `KNTNT_EXTRACTOR_TABLE_CHUNK_BYTES` first, since it is now the knob that most often wants lowering.
- The row-count fixtures that pinned this ADR were all narrow-rowed and all passed throughout: the suite gained a few-fat-rows fixture, which is the shape that discriminates.
