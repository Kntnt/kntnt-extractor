# Every purging actor takes the tick lock, an ownerless artifact is reclaimed server-side after a grace period, and `state=all` is announced through `honours`

Three gaps compounded into one blind spot: nobody could say what was left on a site, or why. `consume()` and `cancel()` both called `Job_Store::purge()` — the same irreversible deletion of a job's artifact and working directory the TTL sweep reaches disk through — without taking the per-job advisory lock every other purging actor already took. `Job_Store::lock()`'s own docblock named the tick driver and the sweep as the lock's users and did not name consume or cancel, even though `purge()`'s docblock named all three as its callers. A cancel landing mid-tick could therefore delete the directory a live build was still writing into, and if the driver's `Artifact_Builder::publish()` rename won that race, a sealed artifact landed in the *served* downloads directory for a job whose record had just been deleted — reachable by no id, ownerless from that moment on, and invisible to the sweep, which walks job records and had none for it. `GET /extractions` compounded the third gap: it lists only the caller's non-terminal jobs, so even an ordinary failure's residue — a record the sweep did not yet touch — was invisible from the API, a fact the sweep's own code comments already conceded.

## The lock has one owner, and now every purging actor takes it

`Job_Store::lock()` states its own contract: the single owner of the per-job advisory lock, taken by every actor that must not touch a job another is actively building through. `consume()` and `cancel()` now take it before calling `purge()`, with `try`/`finally` around the call exactly as `Sweeper::sweep()` already does, so `purge()`'s three documented callers now agree about how they reach it. A lock that cannot be taken is answered `409 kntnt_extractor_locked` — never a silent skip, and never a wait: the acquisition is the same non-blocking `flock( LOCK_EX | LOCK_NB )` the tick and the sweep use, so a caller racing a live build is told plainly to retry rather than left guessing why nothing happened, or left waiting on a request that might hold a live PHP worker for as long as the build runs. `cancel()` reaches a job in any state it owns — queued, running, or ready — so it is the caller most likely to race an active tick; `consume()` only ever reaches a `ready` job, already terminal for the builder, so the lock there should not normally fail, but the same 409 is the honest answer on the rare occasion it does (a lock file that cannot even be opened, say). This closes the race for every future purge: `consume`, `cancel`, and the sweep now all hold the same lock before touching a job's disk state, so a live build is never deleted out from under itself by any of the three.

## An artifact with no record has no owner, so reclamation stays server-side

The lock fix closes the race going forward; it does nothing for whatever the race already left behind, nor for the narrower crash window between `Artifact_Builder::publish()`'s rename and a tick's own record save landing (the tick still commits its `ready` state after the artifact exists on disk — see `Dispatcher::advance_one_chunk()`). `Job_Store::orphaned_artifacts()` is the answer: it enumerates the served downloads directory for a file that no live job record claims. A job's `artifact` filename is minted once, at `create()`, before the job ever runs, so for as long as *any* record of the job survives on disk — queued, running, ready, or terminal — that filename is claimed, whatever state the job is currently in. A file the enumeration finds unclaimed can therefore only be residue: nothing a `GET /extractions` change could ever surface, because a listing reports jobs, and an orphaned artifact is precisely the file for which no job exists to report. This is why reclamation had to move into the sweep rather than becoming a caller-facing delete: there is no id to address it by, no owner to scope a request to it, and no verb this plan is willing to add (see the plan's "Out of scope" — no job-management verb of any kind). `Job_Store::delete_orphaned_artifact()` re-validates the same pin `orphaned_artifacts()` already applied — a null-byte guard, the artifact's own filename shape, and a resolved path strictly inside the resolved downloads directory, never following a symlink out — because real time (a whole grace period, possibly a whole further sweep cycle) passes between the enumeration and the deletion, and this codebase's rule is that a destructive call re-checks its own pin rather than trusting an earlier read.

## Why the grace period exists, and why it is the TTL

Reclaiming on sight was rejected outright. `Job_Store::find()` already carries a bounded retry for exactly this shape of problem (issue #20): a state file that is present but transiently unparseable — sampled mid the atomic rename that publishes every save — reads as absent until the retry budget is spent. `Job_Store::all()` calls `find()` once per directory, so a transient read glitch on *one* enumeration can make a perfectly live job's artifact look unclaimed for a moment that is not actually a leak. A grace period is what tells that moment apart from a genuine orphan without inventing a second threshold to reason about: an artifact younger than the grace period may simply not have had its claim catch up yet; one older than the window a live job's own heartbeat keeps fresh is not waiting on anything, because nothing legitimate takes that long. The grace period is the TTL itself, resolved once per sweep call and passed to both the job loop and the orphan reclaim — not a new constant. This project's constants are measured, not chosen (see e.g. [0015](./0015-a-stall-shrinks-the-chunk-and-a-failed-stall-can-be-re-driven.md) on the chunk-budget constants that were not), and the TTL is already exactly this window: the time a *still-recorded* but never-consumed artifact is judged by, one call above in the same sweep. An artifact with no record at all gets no narrower a benefit of the doubt than one that at least still has a record — reusing it says that plainly, and it means a site that has already tuned its TTL for its own hosting reality tunes the orphan's grace period along with it, for free.

## Why the listing stayed owner-scoped

`GET /extractions` gained an optional `state=all` parameter that additionally admits the caller's own terminal jobs — the direct answer to "is there anything of mine still on this site" the plan's motivation asks for. It does not become, even slightly, an administrative view. The owner scope in `list_jobs()` is unconditional and precedes the state check: a job belonging to another user is skipped before the terminal filter is ever consulted, exactly as it already was, so `state=all` cannot widen *whose* jobs are visible, only *which of the caller's own* are. This follows [0012](./0012-identity-dependent-responses-are-never-cacheable.md) directly: `resolve_owned_job()`'s uniform non-owner refusal exists so no endpoint becomes an existence oracle, and a listing that could be asked to reveal another user's terminal jobs would be exactly that, one layer up. A terminal entry also carries a deliberately narrow shape — id, state, and the two timestamps every entry already carried, and nothing else: no `progress` (there is none left to report once a job is terminal) and no `download_url` (`list_jobs()` has never returned one, terminal or not, and every terminal job's artifact is gone by the purge that ended it). The consuming repository's stated need is exposure, not administration — it wants to know whether sealed data of its own is still sitting on the site, not a console to manage other people's jobs from — and the response shape says only as much as answering that question requires.

## Why `state` is announced through `honours`, not a version bump

`state` ships additive and absent-by-default: an old client that has never heard of the parameter sends no `state` at all, and the default response is unchanged in every byte, which `tests/Integration/extractions-list-test.php` pins directly by re-running the pre-existing assertions unmodified against the same fixtures. Under [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md), `API_VERSION` bounds the *artifact's* shape — the container's framing, segments per resource, the sealed index, reassembly order — and this plan changes none of it: no wire format, no segment, nothing `kntnt-wp-skills` reads off the sealed container is different. `state` is a REST-only, additive request parameter, exactly the shape `strict` was when it forced [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md) to exist in the first place, so it is named in `Status_Controller::HONOURED_BEHAVIOURS` — sorted, alongside `attempts`, `chunks_done`, `disclosure`, `skipped_files`, and `strict` — rather than bumping the integer a second time for a change [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md) already drew the boundary to exclude. `API_VERSION` stays `7`.

## Consequences

- `Job_Store::lock()`'s three documented purging callers — consume, cancel, and the sweep — now all take it before deleting anything; a lock the caller cannot take is `409 kntnt_extractor_locked`, never a silent skip and never a blocking wait.
- `Job_Store::orphaned_artifacts()` and `Job_Store::delete_orphaned_artifact()` give the sweep a way to reach a served artifact no job record claims, pinned the same way every other destructive path in this store is pinned (null-byte guard, shape check, resolved-strictly-inside, no symlink followed), and bounded to `ORPHAN_SCAN_LIMIT` entries per call so the enumeration itself cannot become unbounded on a site that has accumulated many files — an entry past the bound is simply examined on the next sweep cycle instead.
- `Sweeper::sweep()` reclaims an orphaned artifact past its grace period (the resolved TTL) on the same call that expires stale job records; the reclamation is not represented in the method's `array<int, Extraction_Job>` return value, because an orphan has no job to report as expired, only a file to remove.
- The pre-adaptation-stall exemption in `Sweeper::reclaimable()` is untouched by any of this — it governs job records, this plan's new reclamation governs files with no record at all, and the two paths never overlap. **The exemption was retired with the rest of ADR-0015's back-compatibility cluster on 2026-08-21 (#52); see that ADR's addendum.** The separation of concerns this bullet states is what survives it: the orphan reclamation still governs files with no record at all, and `reclaimable()` is now a question about terminality alone.
- `GET /extractions` gains an optional `state` query argument, validated by the route's own `validate_callback` against the single accepted value `all` — a malformed value is `400 rest_invalid_param` before the callback runs. The default (`state` absent) is unchanged, proven by re-running the pre-existing listing assertions verbatim. `state=all` additionally admits the caller's own terminal jobs, each reporting only `id`, `state`, `created_at`, and `updated_at` — never `progress`, never `download_url`. The owner scope is unconditional and unaffected: another user's job, terminal or not, is never listed.
- `state` is added to `Status_Controller::HONOURED_BEHAVIOURS`, sorted; `API_VERSION` stays `7`.
- No job-management verb is added. Reclaiming an ownerless artifact remains exclusively the sweep's business; nothing here lets a caller delete, force-cancel, or otherwise act on a job or artifact it does not already have a route to.
