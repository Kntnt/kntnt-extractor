# A define's value discloses only from an allow-list, backed by a heuristic and a per-record discriminator; the version bump is a deliberate compatibility interlock, not a shape claim

`GET /environment` read `wp-config.php`, harvested every `define()` name it found, and resolved each one's live value — except a deny-list of six shapes: four exact names (`DB_PASSWORD`, `AUTH_KEY`, `SECURE_AUTH_KEY`, `LOGGED_IN_KEY`), anything ending `_SALT`, and anything beginning `NONCE_`. That list covers WordPress core's own secrets completely and nothing else. `wp-config.php` is precisely where the WordPress world conventionally puts everything else a site owner never wants leaving the server: SMTP passwords, JWT signing secrets, S3 and other API keys, licence keys, secondary database credentials, third-party service tokens. None of those match any of the six shapes, so all of them came back in plaintext to any caller who cleared the endpoint's capability gate.

This is not a theoretical gap. A saved response from a real extraction run against a client site returned 24 defines. Every core secret was correctly `null`. `DB_NAME`, `DB_USER`, and `DB_HOST` carried values, which is correct and stays correct under the allow-list below — they are layout facts a migration needs, not credentials. Exactly one real third-party secret came through in cleartext: `KNTNT_PAPAPI_KEY`, a 40-character API key, matched by none of the six deny-list shapes, which then sat in a local scratchpad for three days. That response is the whole case for this decision, and it validates the allow-list's shape against an observed outcome rather than a belief about one.

**A deny-list of secrets fails open: every define nobody thought of is disclosed. An allow-list fails closed.** `Environment_Controller::is_disclosable_define()` now discloses a value only when the name is one of sixty-two curated layout and behaviour facts (`ABSPATH`, `WP_CONTENT_DIR`, `DB_NAME`, `WP_DEBUG`, and similar — install paths, URLs, the non-secret database connection facts, multisite topology, core's own behavioural toggles) or one an operator has explicitly opted in, **and** the name matches none of a further heuristic backstop of substrings (`KEY`, `SECRET`, `TOKEN`, `PASS`, `SALT`, `NONCE`, `AUTH`, `CREDENTIAL`, `PRIVATE`, `LICEN`, `API`), matched case-insensitively, applied *after* allow-list membership and never before it — so the backstop can veto an allow-listed name, but no allow-listed name can bypass it. The backstop exists because the allow-list is curated by a person today and will be wrong about tomorrow's core define, a third-party plugin's define, or a name added to the allow-list by mistake; a name-shape heuristic is the only mechanism here that generalises past whatever has already been anticipated. `DB_USER` and `DB_HOST` are allow-listed and `DB_PASSWORD` is not: the first two are layout facts a migration needs, the third is the credential.

**Names are still disclosed for every define; only values are gated.** The caller needs to know what `wp-config.php` defines to make sense of an install, and a name alone — `KNTNT_PAPAPI_KEY`, say — discloses nothing a site's own source control doesn't already show. Withholding names would also break the one property this design depends on: a caller who wants a specific value opted out of by policy can see that the define exists and ask for it through the escape hatch below, rather than never learning it was there to ask for.

**The escape hatch is per-site and explicit, not global.** `disclosable_defines`, read through the existing `Config` seam (`KNTNT_EXTRACTOR_DISCLOSABLE_DEFINES` the constant, `kntnt_extractor_config_disclosable_defines` the filter), unions a site-specific list of extra names into the allow-list. It resolves exactly as `wp_config_path` already does, so it needs no new seam, and a non-list resolved value — a string, a boolean, an associative array — is discarded rather than trusted, so there is no way to spell "everything": the knob can only ever widen disclosure by a finite, named set of extra defines, each still subject to the heuristic backstop like every other name. An operator who genuinely needs a specific unlisted define disclosed states so, once, on the site that needs it; nobody gets that by accident.

## Why `null` alone was insufficient

An earlier draft of this decision ruled a discriminator out of scope, reasoning that a name present with a `null` value already carries the information a caller needs. That reasoning is false, and the consuming client (`kntnt-wp-skills`) proves it: a define whose value is `null` is classified there on its **name alone**, offered to the operator as portable, and rendered into the local `wp-config.php` as `define('X', null);`. `php -l` passes; the smoke test does not check define values; and the result is worse than the define being absent, because `defined('X')` now returns `true`, so whatever plugin owns that constant never falls back to its default and runs with a null key, silently. A version number cannot fix this either: a version tells a caller what the *server* does as a class, and it can never answer a *per-record* fact — even a client that knows the allow-list is active cannot tell a withheld value from a legitimately-null one for one given define, because both look identical on the wire.

The fix is `disclosure`, a per-record, closed three-value string (`included`, `secret`, `not_allow_listed`) on every `defines` record. It is a closed enum rather than a boolean or free text, because the client reports withheld names to a human, and "not on the disclosure allow-list" reads better than a bare name a boolean can't distinguish from "not on any list *because* it looks like a credential" — the two reasons genuinely differ, and an operator deciding whether to open the escape hatch for a name needs to know which. It is a member on the existing record rather than a separate list of withheld names, because a separate list is a join, and a hand-join on define records has already caused one bug in the consuming repository.

**It is present on every record, including disclosed ones, and this is the load-bearing constraint of the whole design.** If the member appeared only when something was withheld, "member absent" would silently become a third state meaning "old server" — and a caller would be back to inferring, which is the exact failure this decision exists to remove. `docs/define-disclosure.md` states this as a MUST for exactly that reason.

## This amends [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md): a named exception, not a silent contradiction

[0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md) narrowed `api_version` to bound *the artifact contract only* — "the container's framing, segments per resource, the sealed index, and reassembly order" — and states plainly: "A behavioural change to a request or response field, however caller-visible, is a `honours` entry instead." Read literally, that rule forbids the bump this decision makes. `disclosure` is a new response field, not a shape change to the sealed container; by 0017's own test it belongs in `honours`, not under a version bump. This ADR does not get to quietly disagree with a rule that landed an hour before it. It amends it, on the record, by naming a second, narrower ground on which `api_version` moves.

**The ground is compatibility, not shape, and it is this: `api_version` also moves when a change would make an already-shipped, unmodified client's *existing* behaviour unsafe against the new server, in a way that client cannot detect and did not opt into.** `honours` is built for one kind of caller-visible change — a capability an old client is free to keep ignoring, because ignoring it reproduces exactly the behaviour that client already had. `strict` is the case that motivated 0017: an old client that has never heard of it keeps hard-failing on a vanished file, which is what it always did. That is safe by construction, for any name ever added to `honours` in the future, precisely because "ignore the unknown field" is the client's own long-standing, correct policy. The define-disclosure change is not that shape. The consuming client does not ignore an unrecognised `null` — it *acts* on it, today, by name-based classification, and ports it into a local file as a literal `define('X', null)`. Before this change, that behaviour was safe only by coincidence: every name the old deny-list ever redacted also happened to be on the client's own auto-excluded list. This decision ends that coincidence on purpose — the allow-list redacts many names (`KNTNT_PAPAPI_KEY` among them) the client's exclusion list has never heard of. Ship this against an unmodified client and its own, already-shipped logic silently writes a real site's `wp-config.php` with a null credential where a real one belongs, while `defined()` reports the constant present and the owning plugin's fallback never runs. Nothing in that path is a bug the client introduces; it is a bug already latent in shipped code, made live by a change on this side that the client cannot see coming and has no way to opt out of, because the field it reasons about (`value: null`) is not new — only what it now means for some names is.

That is the test this ADR applies, and it is different in kind from every other case `honours` covers: not "does an old client miss a new capability," which is always safe, but "does an old client's own existing logic, run unmodified against the new server, produce a result that is wrong in a way neither the client nor its operator can detect." The verified ceiling `kntnt-wp-skills` pins against `api_version` is the only mechanism in this contract that can force "you must update before you touch this server" — the client refuses to run at all against a version above what it has verified. `honours` has no equivalent teeth: an old client that has never heard of `disclosure` does not fail to look for it, because nothing before this change told it to look. The bump is therefore not a claim that this is a shape change of the artifact; it is a deliberate compatibility interlock, invoked because the alternative is a server change that turns a latent, coincidence-covered client bug into a live one with no client-visible signal at all. `docs/adr/0017`'s rule stands for every case that is not this one: a `honours` entry never needed a bump before, and after this decision it still doesn't, unless the same test — an old client's shipped behaviour, not merely its feature set, becomes unsafe — is met again. `CONTEXT.md`'s **API version** entry is updated to record this second, narrower ground alongside 0017's shape rule.

## Consequences

- `Status_Controller::API_VERSION` moves from 6 to 7. This is a coordination cost, not a formality: `kntnt-wp-skills` pins a verified ceiling on this value and refuses to run against anything above it until that ceiling is raised in a coordinated release, and until then, this plan does not block writing or merging — only installing it where an extraction run is pending.
- `kntnt-wp-skills`'s own mirrored deny-list (`is_secret_define()` at `scripts/discovery.py:193-205`, and the wider `scripts/classify.py:64-92`) must move to the allow-list model in the same coordinated release referenced in `plans/README.md` → "Cross-repo release order". Until their fix lands, an old client must not be pointed at a server carrying this change.
- `disclosure` is also added to `Status_Controller::HONOURED_BEHAVIOURS`, alongside the version bump rather than instead of it: the field is new caller-visible surface a client can check for by name like any other honoured behaviour, even though what it reports on shipped under a coordinated bump rather than silently.
- Every `defines` record on `GET /environment` now carries `{ name, value, disclosure }`. `disclosure` is one of exactly `included`, `secret`, `not_allow_listed`, present unconditionally; a reader MUST treat an unknown fourth value as withheld (`docs/define-disclosure.md`).
- The allow-list's *membership* — which names are on it — is deliberately not part of the versioned contract and may change without a further bump, as `docs/define-disclosure.md` states; the *protocol* (the meaning of `null`, the discriminator's three values, the present-on-every-record rule) may not change without one.
- An operator relying on a currently-unlisted define must now opt in explicitly, per site, through `disclosable_defines`. This is accepted as the cost of failing closed by default.
- `classes/Restricted_Path.php`'s file-layer deny-list has its own, separate gaps (editor droppings beside `wp-config.php`, matching on the unresolved rather than resolved path). They are a real finding, deliberately out of this decision's scope.
