# Every response in the plugin's REST namespace is identity-dependent and is therefore marked uncacheable, and every refusal names its own cause

Every response the plugin gives — the payloads, the refusals, and the responses to routes that did not match — is a function of who asked, so no cache may retain any of them. A single filter on `rest_post_dispatch`, scoped to the `kntnt-extractor/v1` namespace, stamps `Cache-Control: no-store, no-cache, must-revalidate, max-age=0` and `Vary: Authorization` onto every response regardless of its status code or the request's authentication state, and additionally fires `do_action( 'litespeed_control_set_nocache', … )` because LiteSpeed's page cache decides through its own control API rather than through the response headers. Alongside it, the authorization gate stops answering every refusal with one opaque code: a request that resolved to no WordPress user answers `401 kntnt_extractor_not_authenticated`, an authenticated caller missing either half of the two-capability composition answers 403 naming which capability is missing, and `GET /status` reports the authenticated caller's `user_login` and both capability holdings so the identity question can be asked directly instead of inferred.

The rule is unconditional because the response that must not be cached is exactly the one WordPress does not protect. Core sends its no-cache headers only for a request it considers authenticated, and an authentication attempt that fails to resolve a user is not authenticated: `wp_authenticate_application_password()` short-circuits silently on an unknown login, returning no error at all, so the request proceeds as anonymous and the resulting refusal goes out looking like a perfectly ordinary cacheable anonymous error. On a site behind a page cache — the case that produced this decision, a production LiteSpeed install — that refusal is then stored against the URL and replayed to every later caller, including one presenting entirely correct credentials. One mistyped username locks the endpoint out for everyone until the cache is purged, and appending a unique query parameter to the same request makes it succeed, which is the tell. A guarantee that holds only for the authenticated case would therefore protect only the responses that were never in danger.

Marking cacheability per controller was considered and rejected. The endpoints are added one issue at a time, each with its own controller, and the response most in need of the guarantee is the one no controller writes: the refusal the permission callback returns, and the 404 for a route inside the namespace that matched nothing. `rest_post_dispatch` is the single seam every one of those passes through — core converts a `WP_Error` to a response before the filter runs, and applies the filter even when authentication failed before dispatch — so the guarantee is stated once and cannot be forgotten by a later endpoint. Scoping it to the namespace rather than filtering `rest_send_nocache_headers` globally keeps the plugin from making cacheability decisions on behalf of the rest of the site.

The distinct refusal codes exist because the generic one made the fault above undiagnosable. `kntnt_extractor_forbidden` at 403 for every refusal, anonymous callers included, meant a stripped `Authorization` header, an unknown username, a revoked capability, and a cached error response all presented identically to the caller, and a client could only guess between them by comparing statuses across several endpoints — an inference a cached response mimics exactly. This reverses the earlier choice, recorded in the gate's own documentation and pinned by an acceptance criterion, to answer an anonymous caller 403 rather than the 401 WordPress would substitute, on the reasoning that an anonymous caller is definitionally missing the Operate capability. That reasoning is sound about capabilities and wrong about diagnosis: the two failures have different remedies — supply credentials versus grant a capability — and a status code that cannot tell them apart withholds precisely the information the caller needs. [0002](./0002-authn-app-password-authz-operate-plus-manage-options.md) is unaffected: the composition, the capabilities, and the order of validation before authorization are all unchanged; only the vocabulary of the refusal is.

Extending `GET /status` rather than adding a `/whoami` endpoint follows from what `/status` already is — the handshake a client makes before anything else, reachable without credentials. Adding the identity report to it is purely additive: an anonymous request receives byte-for-byte the response it always did, so no existing client breaks, and a client that does send credentials gets the answer in the call it was making anyway. A separate endpoint would have been one more route to gate, and would have had to be gated on something — which is the very question it exists to answer.

## Consequences

- Every response under `kntnt-extractor/v1` carries `Cache-Control: no-store, no-cache, must-revalidate, max-age=0` and `Vary: Authorization`, and marks itself uncacheable to LiteSpeed, whatever its status code and whether or not a user was authenticated.
- A new endpoint in the namespace inherits the guarantee with no wiring of its own; an endpoint that must be cacheable would have to argue its way out of this decision first.
- The authorization gate's refusals are now three codes rather than one: `401 kntnt_extractor_not_authenticated`, `403 kntnt_extractor_missing_operate_capability`, and `403 kntnt_extractor_missing_manage_capability`. `kntnt_extractor_forbidden` survives only where it names an entirely different refusal — a missing per-job tick secret and a job belonging to another user — both of which stay deliberately uniform so that neither endpoint becomes an existence oracle.
- An anonymous caller now receives 401 where it previously received 403. This is a deliberate reversal of the earlier acceptance criterion, and any client that tested for 403 to mean "not permitted" must accept 401 as well.
- `GET /status` reports `authenticated_as` and `capabilities` when — and only when — the request resolved to a WordPress user. The anonymous response is unchanged.
- The refusal codes and the status endpoint's extra members are caller-visible, so shipping them increments the API version (see [0005](./0005-github-releases-self-hosted-update-checker.md)); the cache headers alone would not have.
- A client cannot rely on an intermediary honouring the headers, and a cache-busting query parameter remains a reasonable belt-and-braces measure on the caller's side against an intermediary this plugin cannot reach or an installation older than this decision.
