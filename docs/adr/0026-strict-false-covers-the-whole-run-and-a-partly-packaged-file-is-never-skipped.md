# `strict: false` covers the whole run, and a partly packaged file is never skipped

`strict` stops being a create-time filter and becomes a property of the run. Under `strict: false` a file that no longer exists when its chunk is packaged is dropped from the artifact, appended to the job's skipped list, and reported by the poll exactly as a create-time skip is — instead of failing the job and discarding every table and file already packaged. Under `strict: true` nothing changes at all.

Two edges are drawn tightly around that, and they are the substance of this decision rather than caveats on it.

**Only a file that is *gone* is skippable.** The create path already sorts a requested path three ways ([0003](./0003-generic-manifest-and-table-list-no-server-side-categorisation.md)): kept, vanished, or out of bounds — where a null byte, a `..` segment, and a path resolving outside the installation root are out of bounds and are never a skip, even when the target does not exist. The packaging path now makes the same three-way distinction instead of collapsing every failure to resolve into one error, and the distinction is the same one, drawn by the same rules. A path that exists and cannot be read is not gone either: it stays the hard error plan 005 made it, in both modes.

**A file that has already contributed a segment cannot be skipped.** If a file vanishes between two of its own parts, the container already holds its earlier bytes. Skipping there would publish a file truncated at whatever offset the deletion fell on, and `docs/container-format.md` gives a reader nothing to notice that with: a reader reassembles a file by concatenating every segment carrying its name, and a short result is indistinguishable from a short file. That is the failure mode this project has repeatedly chosen to fail loudly rather than accept, so the job fails, with a message that says the file was deleted after part of it had been packaged.

## Why the create-time filter was never the whole thing

`strict: false` was built for the gap between the `GET /files` walk and the `POST`. The gap it left open is the one between the `POST` and the last chunk, and on a large installation that second gap is the entire run. A manifest is a snapshot; a live site is not, and it does not stop being live because an extraction is in progress.

The evidence is `docs/measurements/2026-08-18-production-run.md` §3: a six-hour extraction died at 47,504 of 48,559 files — 97.8 % — with 186 of 186 tables already packaged, and everything discarded at fail time. The last chunk begun, nine seconds before the job died, was `wp-content/uploads/2026/08/kntnt-extractor.zip`: the release archive that installed the very build the run depended on, plausibly removed by WordPress's own upgrade cleanup mid-run.

**That attribution is an inference and is recorded as one.** The server's own account of the failure was the generic fallback sentence, which is exactly the gap [0022](./0022-a-relayed-throwable-message-may-carry-a-path-or-a-query-fragment.md) and issue #25 closed. What the inference rests on is four converging facts — the file is the last chunk begun, the failure timestamp matches it to the second, the file is confirmed absent today while its immediate neighbour is not, and its neighbours transferred fine — and not on anything the plugin reported. The decision does not need the inference to be right: a file vanishing during a multi-hour packaging window is ordinary on a live site whatever ended that particular run, and the next occurrence will be evidence rather than inference because #25 landed first.

## What this does not fix

- It does not make the failed run recoverable. That container is gone.
- It does not stop a file from vanishing. Nothing server-side can.
- **It does not make a vanished file's absence harmless to the copy.** A skipped file is missing from the artifact and the caller learns which. This widens where the `strict: false` contract *applies*; it does not improve what that contract *guarantees*.
- It does not address the per-part cost that made the run six hours long in the first place (`docs/measurements/2026-08-18-production-run.md` §1). A shorter run is also a smaller window for this bug, and that half is untouched here.

## The window this narrows and does not close

The packaging path checks whether a file is there and then opens it, and a file can vanish between those two instants. That race is unavoidable without holding an open handle across the check, and the practical remedy is the same skip reached one layer further in. It is written down here so the next person to meet it recognises a known residue rather than a new defect.

## `skipped_files` no longer describes what a build honours, so `packaging_skips` is added

This was the one question in the plan flagged as a real decision rather than a formality, and the answer is that a name is needed.

`honours` exists because absence from it is the only signal a client has ([0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md)), and `strict` is the case that forced the list into existence. Against a 0.6.0 build, `honours` already contains both `strict` and `skipped_files`, and a mid-run deletion still kills the run. A client that reads those two names and concludes it may rely on a long `strict: false` run surviving a deletion is wrong, and nothing on the wire tells it so. That is precisely the `strict` failure one layer up — the shape [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md) calls a maintenance error rather than an inherent limit — and the release procedure's §3 step 3 exists because this omission is invisible to every automated check.

`skipped_files` keeps its own meaning and stays: it names the *member*, which an old client is still right to read the same way. `packaging_skips` names the *reach* — that a skip is decided for the whole run and not only at create time — which is the fact a caller planning a multi-hour extraction actually needs. Neither name implies the other, which is why both are on the list.

## Why neither version number moves

**`API_VERSION` stays `7`.** Under [0017](./0017-api-version-bounds-the-artifact-contract-honours-reports-what-a-build-does.md) the integer bounds the artifact's shape — the container's framing, segments per resource, the sealed index, reassembly order — and none of it moves. Under [0018](./0018-a-defines-value-discloses-only-from-an-allow-list-with-a-per-record-discriminator.md)'s narrower second ground it also moves when an already-shipped client's existing logic would become unsafe against the new server, undetectably and without its consent. No member is added and none removed; what changes is that an existing list may hold entries it could not before, and may grow after the `201` first reported it.

**That last part is the half worth checking on the other side rather than asserting here.** The ticket reports that `kntnt-wp-skills` already subtracts `skipped_files` when it reconciles what was packaged, in which case a mid-run addition composes with logic that has shipped and the integer is right to stay where it is. **Nothing in this repository verifies that**, and it has not been verified from here — it is one repository's report about another's code. What the client must actually hold to is narrow and stated plainly so it can be checked in one reading: `skipped_files` is no longer settled at create, so a client that reads the `201`'s list and never re-reads the poll's will under-count what it is missing. If that is what an installed client does, this *is* [0018](./0018-a-defines-value-discloses-only-from-an-allow-list-with-a-per-record-discriminator.md)'s second ground — already-shipped logic made unsafe undetectably — and the integer would have to move. The `packaging_skips` name above is what lets a client tell the two builds apart either way, which is the cheaper half of the answer and does not depend on the check.

**`SCHEMA_VERSION` stays `8`, and that needs saying because the plan expected otherwise.** The record must carry `strict` for the packaging path to see it, and plan 018 was written on the premise that adding a field to a released schema is a bump and therefore the operator's call. That premise did not survive the two decisions that landed between the plan being written and being executed. [0024](./0024-below-1-0-there-is-no-backwards-compatibility-and-the-single-site-is-why-that-is-decidable.md) removed compatibility with this plugin's own earlier records as a constraint entirely — one site, no migration, ever — so the bump would be a signal to a reader that does not exist. And issue #25 had already added `thrown` to schema 8 *after* 0.6.0 shipped, on the reading `SCHEMA_VERSION`'s own docblock now states: an additive key whose absence is read tolerantly, and which no older release needs to understand, does not move the number. `strict` is written only when it is `false` — the same omit-the-default shape `skipped_files`, `thrown` and the attempt log already use — and an absent or ill-typed key reads as `true`, which is the hard fail every record written before this change already had. A record from 0.6.0 therefore keeps behaving exactly as it did. `rule R5`, cited in the plan for this, exists nowhere in this repository.

## Where the mid-run skip is written, and why it costs a full record write

[0014](./0014-the-persisted-record-is-split-so-a-save-is-bounded.md) splits the record on what is unbounded: the selection and `skipped_files` live in the selection file, everything a tick changes lives in the state file, and `Job_Store::save()` — called twice per packaged chunk — rewrites only the second. A mid-run skip is the first mutation to touch the first half.

Two placements were weighed. Putting the mid-run skips in a *second*, state-half field would keep every write on the ordinary path, but it makes an unbounded list part of the document rewritten twice per chunk — the exact cost [0014](./0014-the-persisted-record-is-split-so-a-save-is-bounded.md) exists to remove — and it splits one caller-facing concept across two fields. Rewriting the selection file keeps `skipped_files` a single field with a single meaning and pays a full selection write **per skip**, not per save. On the run that motivated this, that is a handful of writes across six hours. The hot path is untouched: `save()` is unchanged, and the driver reaches the wider write only on the tick that actually skipped something.

The two halves are written in the same order `Job_Store::create()` writes them — selection first, state second — so a tick killed between them leaves the skip recorded and the progress not yet advanced. The next tick re-reaches the same file and re-skips it, which is why appending is idempotent. The failure that ordering rules out is the opposite one: progress advanced past a file whose skip was never recorded, which is a file silently missing from both the artifact and the report.

## Consequences

- A long `strict: false` run survives a file being deleted under it, which is the ordinary condition of a live site rather than an exotic one.
- **The artifact is still short a file, and the caller still has to act on `skipped_files`.** Nothing here makes an incomplete copy complete. A caller that ignores the list gets a silently incomplete copy exactly as before — the list is just longer now, and may grow after the `201` that first reported it.
- `skipped_files` is no longer written once. A poll may report more skipped files than the `201` did, and the create response is a lower bound on the final list rather than the whole of it. **A client that reads only the `201`'s list under-counts what it is missing**, and whether the installed `kntnt-wp-skills` does that is the one open check this decision leaves — see the `API_VERSION` paragraph.
- A selection whose files all vanish mid-run publishes a container with no file segments and a skipped list naming all of them. That is the honest outcome of the contract, and it differs from create time, where a selection left empty after the skip is a `404` because there is nothing to start.
- A file deleted between two of its own parts still fails the whole run, and no `strict` value changes that. The run that motivated this decision had three multi-part files in it, so the case is not hypothetical.
- The packaging path now enforces the null-byte and `..` rules the create path enforces, where it previously relied on the resolved path landing inside the root. That is a tightening of a boundary check on a record only this plugin writes, and it cannot reject anything the create path admits.
- One more `realpath()` per file part under `strict: false`, and none under `strict: true`. It sits beside a bounded read and a seal, and no measurement is claimed for it.
