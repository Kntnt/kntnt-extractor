## Read this before starting anything

**Plan 008 is the one that costs a release.** It bumps the REST `api_version`
from 6 to 7, which trips the consumer's verified ceiling: a client meeting a
version-7 Extractor refuses to run at all until its ceiling is raised. That is
the ceiling working as designed. Both halves are planned in
`~/Projects/kntnt-wp-skills/plans/` — see "Cross-repo release order" below.
Every other plan here leaves the wire contract untouched.

**Plans 001–007 and 012 are deliberately release-independent.** None changes the
container format, the REST surface, or `api_version`, so they can land before or
after a release without forcing a coordinated one.

**Plans 013 and 014 are additive and do not move the integer.** Under the
division 014 settles, `api_version` governs the artifact contract and the
ceiling; behaviour a caller opts into is discovered through a capability list.
That is why 014 must land before 013 — the `state` parameter needs somewhere to
be announced.

## What each plan is for, in one line

- **001** — the gate exists and is thorough; nothing runs it automatically, and releases are built straight from committed content.
- **012** — the dumper's MySQL-specific SQL runs only against SQLite's translation of it; the one MySQL-backed test in the repository is about `SHOW TABLE STATUS` and never touches the dumper.
- **002** — a failed database read is currently indistinguishable from the end of a table, so a transient fault publishes a silently truncated dump that reloads without an error.
- **003** — the row budget is rounded up to a 100-row batch before use, so it cannot bind below 100; the stall adaptation keeps halving it anyway, spending about fourteen host kills on a bound that no longer moves.
- **004** — `finalize()` deletes the index sidecar before the container is published, so a crash in that window destroys a finished multi-hour build.
- **005** — a failed `fread()` is cast to an empty string, which resets the stall counter, the heartbeat and the last-progress stamp together, giving a job that spins forever holding the concurrency slot.
- **006** — every segment's plaintext is round-tripped through `php://temp`, which spills to the system temp directory above 2 MB while both default budgets are larger.
- **007** — two `ftruncate` calls that discard nothing, path stats where an open handle is about to exist, and two catalog queries re-issued per table slice.
- **014** — one integer is answering two questions; `strict` shipped without a bump, so no version number can ever distinguish a build that honours it.
- **008** — `GET /environment` returns every non-core `wp-config` define in plaintext, which is where third-party credentials conventionally live. Observed: a 40-character third-party API key left the server and sat in cleartext on the operator's laptop for three days.
- **013** — `consume` and `cancel` purge without the tick lock, an artifact orphaned in that window is unreachable by the sweep, and no caller can ask what of theirs is still on the site.
- **009** — the container format is defined in a class docblock here and read only by another repository; nothing here can verify the byte-compatibility claim the project makes about itself.
- **010** — the concurrency ceiling is global but the job listing is owner-scoped and live-only, so a 429 tells the caller nothing about what they are waiting for.
- **018** — `strict: false` is applied only when the job is created, so a file that vanishes between the `POST` and the moment its chunk is packaged still fails the whole run. On a six-hour extraction that window is the entire run, and it is what ended the 2026-08-18 attempt at 97.8 %: `wp-content/uploads/2026/08/kntnt-extractor.zip`, the release archive that installed the very build the run depended on, removed by WordPress's own upgrade cleanup mid-run. **Read its "What this does not fix"** — a skipped file is still missing from the copy.
- **017** — a production run failed at 97.8 % after six hours and the whole record of why is `The extraction failed.`, which is not a message the plugin wrote but `error_of()`'s fallback for a null `error`. No stall reason, so no two-pair limit reading; the failure mode that actually ends runs on this host bypasses the project's cheapest diagnostic entirely. **Read its "What this does not fix" section** — a process killed outright still records nothing, and the plan says so.
- **011** — the sweep spares one failed record forever, which keeps a cluster of schema back-compatibility branches permanently reachable with no recorded condition for retiring them.
- **019** — `Table_Dumper` re-asks the database whether a table exists and what its primary key is on *every slice of every table*, and plan 007 dropped the fix rather than decide whether a memo may refuse on its own knowledge. It may not: it re-reads on a miss, which keeps ADR-0003's rule verbatim and keeps the saving.
- **020** — ADR-0014 claims an artifact from this release is byte-compatible with one from 0.5.1, and nothing here can check it. A container cut from `v0.5.1`, a test-only reader written from the specification rather than from the writer, and every expectation computed from the format's own arithmetic — so re-cutting the fixture cannot turn a red test green.

## Findings considered and rejected

Recorded so nobody re-audits them.

- **The 404-before-403 ordering on `POST /extractions`.** ADR-0003's Consequences state it explicitly: "A resource name that doesn't already exist … is rejected before any capability check runs, and the 404 names every offender." Settled, not a finding. What was *not* settled at the audit was the unbounded work an anonymous caller can provoke — no `args` schema, no element cap and no body-size cap at the time, while `validate_payload()` runs a `realpath()` per path and two `SHOW TABLES` before `authorize()`. That half was real and was not selected for planning at the time. It was planned afterwards as **015** and **bounded by #26** (`3084e81`, ADR-0020): `KNTNT_EXTRACTOR_MAX_BODY_BYTES` refuses an oversized raw body with a `413` before `json_decode()` sees it, and `KNTNT_EXTRACTOR_MAX_SELECTION_ELEMENTS` refuses an oversized selection with a `422` as soon as the three arrays' shape is settled — ahead of the `realpath()` walk, the catalog queries and the capability gate alike. Bounded, not closed, and ADR-0020's Consequences say so: there is still no `args` schema (plan 015's Scope requires manual checks instead), one uncredentialled request can still force up to `max_selection_elements` `realpath()` calls before `Authorizer::authorize()` is reached, and how *often* one may be sent is a hosting-layer control this plugin has no seam for. **Corrected under #42:** the body cap refuses before this plugin's `json_decode()`, not before core's — see ADR-0020's addendum.
- **`sslverify => false` on the loopback tick** (the `wp_remote_post()` argument array in `Dispatcher::nudge()`). WordPress core does the same in `spawn_cron()`; this is the platform convention for a loopback, not a weakening peculiar to this plugin. Worth at most routing through core's `https_local_ssl_verify` filter instead of hardcoding.
- **Splitting `Job_Store`, `Dispatcher` or `Extractions_Controller`.** Measured on *code* rather than lines they are 2–3× the repo median, not an order of magnitude — `Job_Store` is 1136 lines of which 697 are comments. `Dispatcher` does have a real seam around the stall policy, but that is exactly the code the unreleased work is still fixing bugs in; extracting it mid-churn buys navigability at the cost of every reviewer's mental map. Revisit after the next release, once the stall logic has been quiet for one.
- **Renaming `Audit_Log`'s filter to match the `Config` seam's convention.** ADR-0006 published `kntnt_extractor_log_retention_days`. Renaming it breaks a documented override to gain nothing observable. A one-line comment saying the deviation is deliberate is the only change with a positive return.
- **Coarsening segments into multi-file packages.** Already decided against by the project, and nothing in this audit changes the reasoning: it needs an in-band manifest, an `api_version` bump, a reader change and a raised client ceiling, and it does not remove the per-*file* cost that no packaging scheme avoids.
- **Repeated `wp_upload_dir()` calls in `Job_Store::base_path()`.** CPU-bound and cached by core; irrelevant against a 210 ms per-chunk budget.
- **Telling a refused caller what is holding the concurrency slot** (plan 010, decided 2026-08-16; full execution record in that plan file). Every 429 the consuming client actually evidences is its *own* sequencing — a bootstrap job racing its own main job, or its own stranded job from an aborted run, which its pre-flight sweep already clears — never contention between administrators. And the client's handling is a deliberate hard stop that never parses the body (ADR-0018 in `kntnt-wp-skills`), so enriching the payload would change no automated behaviour; it would only read better in a human post-mortem, at the cost of a documentation and test round in both repositories. The wider variant — a listing that admits another user's job — is moot: plan 013 already built the owner-scoped half (`GET /extractions?state=all`), and the rest would require weakening ADR-0012's uniform refusal. **Reopen if** the client's 429 handling becomes an automated wait-or-intervene decision that needs occupant data, or if a real inter-administrator contention case is actually reported. No `api_version` bump would be involved either way (ADR-0017 as amended by ADR-0018).
- **Adding unit tests.** This project has deliberately chosen end-to-end integration tests in WordPress Playground over a unit layer. Not a gap.

## Findings surfaced but not selected for planning

Real, verified, and left for a later pass. Listed so they are not lost. A finding closed since is annotated in place rather than deleted, so a reader can still see what the finding was and what closed it.

- **The restricted-path deny-list misses editor droppings.** `.wp-config.php.swp` (a Vim swap file containing the whole file's text), `#wp-config.php#`, `wp-config.bak.php` and `wp-config.old` all pass `classes/Restricted_Path.php:42-47`, while ADR-0011 names "editor droppings" as exactly the family it covers. The root-only key-material patterns also predate `id_ed25519`/`id_ecdsa`.
- **The deny-list is evaluated on the caller's unresolved string.** `Restricted_Path::matches()` runs at `classes/Rest/Extractions_Controller.php:788`, before `classify_files()` resolves anything at `:810`, and is never re-checked at packaging time. An in-root symlink with an innocuous name pointing at `wp-config.php` passes.
- **`POST /extractions` was a check-then-act on the concurrency slot** — it asked `Job_Store::has_free_slot()` whether the slot was free and then, as a separate step, wrote the job that takes it, while the resume path already did the take-then-re-check dance correctly in `Dispatcher::resume_failed()`. **Fixed by #36** (`2279c15`, completed by `e611c7a`): `Extractions_Controller::create()` now persists the job — which is what takes the slot — and only then confirms with `has_free_slot( 1 )` that nothing else took it in the window, and a create that lost that race hands the slot back under the losing job's own tick lock, as every other purging actor does (ADR-0019), leaving a job whose lock it cannot take standing for the TTL sweep. The first `[Unreleased] → Fixed` entry in `CHANGELOG.md` is the full account. The original `:230`/`:241` citations named code this fix replaced and are dropped rather than renumbered.
- **Unbounded unauthenticated work on `POST /extractions`** — see the rejected-findings note above. **Bounded by #26** (`3084e81`, plan 015, ADR-0020): the two additive caps `KNTNT_EXTRACTOR_MAX_BODY_BYTES` and `KNTNT_EXTRACTOR_MAX_SELECTION_ELEMENTS` refuse an oversized request before the `realpath()` walk, the catalog queries and the capability gate. Bounded, not closed — what one request may cost is capped, how often one may be sent is not.
- **The Operate capability survives uninstall** when granted per user, which is what `README.md:45` documents. `Installer::deactivate()` removes it from the `administrator` role only; `Uninstaller::purge_all()` touches no capability.
- **`wp_json_encode()` does not return `false` on invalid UTF-8** as `Job_Store::publish_json()` assumes at `:1046-1054` — it sanitises and returns a mangled string. Reachable through a binary-keyed table's cursor or a non-UTF-8 file path.
- **A malformed `progress` field reads as "the build has not begun"** (the `$progress` assignment in `Extraction_Job::from_array()`, where a value `Build_Progress::from_array()` rejects yields the same `null` an absent field does), which reopens the container with `'wb'` and truncates it. Every neighbouring path at this seam fails closed; this one does the opposite.
- **`tests/Integration/authorizer-tables-test.php:175-176` leaks two global filters** into the 28 test files that run after it (2 `add_filter`, 0 `remove_filter`).
- **The gate runs `--php=8.5`** (`tests/Integration/run.sh:25`) while the plugin declares `Requires PHP: 8.4`. The minimum supported version is never executed.
- **`docs/testing-strategy.md` documents about 14 of the 35 test files** and describes the gate as three steps when it is four.
- **The gate is invisible from `AGENTS.md`**, which tells an agent to ignore narrative docs unless referenced there. Nine `Config` knobs and the whole `GET /environment` endpoint are undocumented outside docblocks.
- **Untested branches**: the lost-lock branch in `Dispatcher::tick()` (the `if ( $lock === null )` early return immediately after `$this->store->lock( $job )`); the durability of the attempt counter *before* the work (in `Dispatcher::advance_one_chunk()`, move the `$this->store->save( $running )` that persists the counted attempt below the `$this->builder->advance( … )` call that follows it, and every stall test still passes); and the published-but-unsaved crash recovery in `Artifact_Builder::advance()` (the `! is_file( $build_path ) && is_file( $download_path )` branch that returns a complete `Build_Step`).

## Corrections to earlier drafts of these plans

Recorded so a reader does not re-derive a mistake that has already been made and fixed.

- **The verified ceiling is not a mechanism.** Earlier notes described the consuming client as stopping against a higher `api_version` as though it were enforced in code. `grep -rn "api_version" scripts/` in that repository returns nothing: no helper has ever seen the number, and both the ceiling and the floor are enforced by the orchestrating model reading skill prose. The suite that appears to bind it is a regex over Markdown. This lowers the cost of bumping the version and raises the value of carrying the number into the client's discovery document.
- **Plan 008 originally ruled a per-record discriminator out of scope**, arguing that a name present with a `null` value already carried the information. That was wrong. `null` on this wire means both "withheld by policy" and "the value is literally null", and the consuming client resolves the ambiguity by porting `define('X', null);` into the local `wp-config.php` — which is worse than the define being absent, because `defined()` then returns true and the owning plugin's fallback never fires. A version number cannot fix a per-record question. Plan 008 now adds the discriminator and explains the reversal in place.
- **The mirrored secret list is duplicated, not drifted.** An earlier note called the consuming repository's second copy "drifted". It is not: the two lists serve different questions ("may this value enter the document" versus "may this be ported") and one is a strict superset of the other. What is genuinely unbound is the `_SALT` suffix and `NONCE_` prefix patterns being written out verbatim in both places with no test tying them — and the agreed fix is to bind the *protocol*, not the membership.
- **No fourth explanation for the two failed production runs.** A cross-repo report initially suggested a client-side false-stall abort had been costing healthy runs; that was retracted, because the script in question is unreleased and absent from the installed client. What survives is narrower and still worth knowing: at the installed version the client carried two independent false-abort mechanisms, and one of them — a 3600-second wall-clock budget — demonstrably fired on a healthy, visibly-advancing run that then had to be re-polled by hand. So any historical "the run died" account that did not record which side gave up first is not evidence about the server.
